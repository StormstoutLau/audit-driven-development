# v3.0 T20 调研报告 — Findings Schema 激活缺口（`category` 生产者缺失）

> **任务**: T20（承接 v3.0 T19 验收遗留 R-1 的**再诊断**）
> **日期**: 2026-10-20 | **作者**: Scott
> **方法**: 本机一手实测（Read / Grep / Python 统计，N=882 全量）+ 2 路并行调研（内部代码考古 / 外部规范与惯例）
> **前置事实来源**: T19 验收报告 §7 R-1、T9' 验收报告 §10、`docs/research/2026-10-20-ADD-v3.0-reinforcement-research.md` §7 #12
> **状态**: Step 2 产出（尚未进入设计）

## 0. 执行摘要

T19 验收时把「contract 通道零触发」记为 **R-1（收益待 T12 引入 SAST 语料）**。本步实测证明**该诊断不完整**：

1. **真正的根因是 schema 二元化，不是语料规模。** 项目已有权威 schema [schemas/audit-finding.schema.json](file:///f:/Coding/audit-driven-development/schemas/audit-finding.schema.json)，其中 `category` 是**必填字段**，枚举为 `signature | behavior | corrective | blind_spot | contract`（`contract` 为合法值）。但**六个转换器全部写 `dimension`，无一写 `category`**；882 条语料中 `category` 缺失率 **882/882 = 100%**。
2. **`dimension` 是只写不读的死元数据，且词表失控。** 882 条中出现 **10 种**取值（`security` 805 / `functional` 50 / `structural` 8 / `error_handling` 4 / `architecture` 2 / `api_correctness` 2 / `validation` 1 / `scope` 1 / 缺失 9），除测试外**无任何消费者**。
3. **`l4_eligible` 才是决定"结构性验证是否发生"的开关**：bigvul / cvefixes / defects4j 使用方硬编码 `l4_eligible: False` ⇒ **855/882（96.9%）条从不进入 L4**；仅 **27 条（3.1%）**因字段缺省（默认 `True`）可到达 L4，而现有语料中**没有任何一条来自 semgrep / codeql**（两者的转换器虽写 `l4_eligible: True`，但其产物未进 benchmark）。
4. **因此 T9'/T19 的结构化通道是"双门同时关闭"**：`category`/`analysis_kind` 无生产者（门 1）+ `l4_eligible=False`（门 2）。即使按 R-1 把语料扩到 5000 条，**只要转换器仍不写 `category`，通道 A 依旧 0 命中**。
5. **附带发现一个现网缺陷**：[issues_tracker.py](file:///f:/Coding/audit-driven-development/scripts/issues_tracker.py#L43) 用 `finding["category"]` 强取，任何转换器产物在 Phase 4 生成 `issues.json` 时都会 **KeyError**；[inter_rater.py](file:///f:/Coding/audit-driven-development/scripts/inter_rater.py#L117) 则把所有转换器产物归入 `"unknown"` 桶，使 `--per-dimension` 的 kappa 计算失去意义。

**结论**：T20 应定位为「**让已交付的两个确定性能力真正可被触发**」的 schema 对齐任务，成本 **S–M**，且是 T12（语料扩展）的**硬前置**。核心设计约束：**只增不删**（保留 `dimension` / `l4_eligible`），**不可映射即省略**（不为凑字段编造 `category`）。

## 1. 背景

### 1.1 问题链

```
T19 验收（59/59 PASS）── 但 882 条语料上 contract_related = 0 条
        │
        ├─ 记为 R-1「收益待 T12 引入 SAST 转换器语料」 ← 本次证明该诊断不完整
        │
        └─ 实测根因：
             ├─ 门 1：无 producer 写 category / analysis_kind（schema 漂移）
             └─ 门 2：l4_eligible=False 的 584 条根本不进 L4
```

### 1.2 为什么必须在 T12 之前做

T12 的目标是把 benchmark 从 882 扩到 5000+。若先扩语料：

- 新语料由**同一批转换器**生成 ⇒ `category` 缺失率仍为 100% ⇒ T19/T9' 通道 A 仍 0 命中；
- 而 T12 引入的第三方语料（ARVO / CWE-Bench-Java / OWASP Benchmark / Juliet）需要**新的转换器**，届时 schema 若不先定，新转换器会复制既有漂移。

⇒ **schema 对齐是 T12 的前置条件**（顺序不可交换）。

### F-4 canonical schema（既有，非本次新建）

[schemas/audit-finding.schema.json](file:///f:/Coding/audit-driven-development/schemas/audit-finding.schema.json)（draft-07，v0.2 引入）：

- `AuditFinding.required = [id, severity, category, evidence, spec_ref, claim, confidence, fix_cost]`；
- `Category.enum = ["signature","behavior","corrective","blind_spot","contract"]`；
- `AuditFinding.additionalProperties = false` ⇒ **`dimension` / `l4_eligible` 在该 schema 下非法**；
- `EvidencePointer.required = [file, line_start, line_end]` 且 `additionalProperties: false` ⇒ 转换器写的 `cwe`/`owasp`/`rule_id`/`source` 亦非法。

## 3. 外部惯例与规范（一手来源）

| # | 结论 | 来源 |
|---|---|---|
| X-1 | **SARIF 2.1.0 的 `result` 没有 `category` 概念**。承载分类的是：`ruleId`（稳定规则 ID）、`ruleIndex`、`properties`（任意 property bag）、`taxa`（taxonomy 引用）、`kind`（pass/fail/…）、`level`（error/warning/note/none）。规范仅在 taxonomy 意义上使用 category/taxon | [OASIS SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html) §3.27.5/3.27.8/3.27.9/3.27.10、§3.8.1 |
| X-2 | **Semgrep `metadata.category` 是受控枚举**：`best-practice` / `correctness` / `maintainability` / `performance` / `portability` / `security`；另有 `subcategory` = `vuln` / `audit` / `secure default` | [Semgrep Registry 要求](https://semgrep.dev/docs/contributing/contributing-to-semgrep-rules-repository) |
| X-3 | Semgrep 的 `dataflow_trace` 在 schema 中标 EXPERIMENTAL 且**仅 taint finding 出现**；跨文件 trace 属 **Pro Engine / Semgrep Code**，CE 仅单函数 taint。**CE 是否实际输出该字段无官方逐字说明** ⇒ 不得作为可靠输入 | [Semgrep JSON/SARIF](https://semgrep.dev/docs/semgrep-appsec-platform/json-and-sarif) · [Pro Engine data flow](https://semgrep.dev/docs/semgrep-code/semgrep-pro-engine-data-flow/) · `[unverified]`（CE 实际输出） |
| X-4 | **CodeQL** 用 `ruleId` + 规则 `@tags`（`security` / `quality` / `external/cwe/cwe-089`）表达类别，GitHub code scanning 从 `properties.tags[]` 读取；`@kind path-problem` 时 result 带 `codeFlows` | [CodeQL SARIF 输出](https://docs.github.com/en/enterprise-server@3.3/code-security/code-scanning/codeql-cli-reference/sarif-output) · [query metadata](https://codeql.github.com/docs/writing-codeql-queries/metadata-for-codeql-queries/) |
| X-5 | 聚合系统的同类字段**多为开放字符串**：DefectDojo `type`（报告级 Test Type）+ `vuln_id_from_tool`（扫描器 ID）；GitHub 用 `ruleId` + 开放 `tags[]` | [DefectDojo generic parser](https://docs.defectdojo.com/supported_tools/parsers/file/generic/) · [GitHub SARIF 支持](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support-for-code-scanning) |

**可推导的三条硬约束**：

1. **不存在"上游直接给我们 `category`"的路径** —— SAST 元数据里没有 `contract` / `blind_spot` 这类**审计透镜语义**。上游能给的最多是 `security`/`quality` 这类**领域**标签。
2. ⇒ `category` 的**权威生产者只能是 ADD 自己的审计透镜（Phase 2）**；转换器只能做**保守映射**（能映射则映射，不能则省略）。
3. ⇒ 想让 T19 的 `contract` 通道活跃，**必须有 lens 侧的真实产物**（SKILL.md 已定义 `category: contract` 的透镜），不能指望 SAST 转换器。

## 4. 方案对比矩阵

| 方案 | 做法 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| **A. 单层 schema + 转换器补齐** | 转换器直接写 `category`（映射）+ 补 `spec_ref`/`confidence`/`fix_cost` 占位 | 改动面小、一处 schema | 转换器无法知道 `spec_ref`；占位值会制造**假精确**（`confidence` 编造尤其危险） | ❌ 拒绝 |
| **B. 分层 schema（推荐）** | 保留 `AuditFinding`（透镜产物，**不动**）；**新增** `SastFinding`（转换器产物：`category` 可选、`dimension`/`l4_eligible` 合法、`evidence` 允许工具元数据）；另设**映射表** | 只增不删；不污染透镜 schema；不编造 `spec_ref`；可用 schema 机械校验 | 需维护两份 schema + 映射表 | ✅ **推荐** |
| **C. 放宽单一 schema** | 把 `additionalProperties` 改 true、`required` 减字段 | 改动最小 | 削弱既有约束（`EvidencePointer` 的"MANDATORY evidence"正是反幻觉基石）；等于放弃 schema | ❌ 拒绝 |

**推荐 B 的关键理由**：`confidence` 是反幻觉链路的核心语义（high=grep+AST / medium=grep / low=推断），**转换器没有"置信度"概念**，给它填任何值都是编造。分层让"SAST 事实"与"审计判断"在类型上分离。

## 5. 风险矩阵

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R-1 | **误映射 `category` 造成错误激活**（例如把 Semgrep 的 `security` 硬映射成 `behavior`，进而让 T19/T9' 分支误判） | 中 | 高（假裁决进入基线） | **不可映射即省略**；映射表按 `(tool, field, value)` 版本化并单测；`category` 缺失时行为必须与今日**逐位一致** |
| R-2 | 收紧 schema 导致 882 条既有语料全部"非法" | 高 | 中（阻塞回归） | **不回溯改语料**；新建 `SastFinding` 而非收紧 `AuditFinding`；校验器只对新产物强制 |
| R-3 | 修 `issues_tracker` 的 KeyError 改变 Phase 4 行为 | 中 | 中 | 用 `.get("category")` + 显式 `"unknown"` 桶；加回归测试断言键集合只增 |
| R-4 | 依赖 Semgrep CE 的 `dataflow_trace`（X-3 未证实） | 中 | 中 | **只在字段确实存在时**写 `analysis_kind`；CE 缺字段 ⇒ 省略 ⇒ 回落文本通道（现行为） |
| R-5 | `l4_eligible=False` 的 **855/882** 条继续屏蔽 L4，使收益看起来仍为 0 | 高 | 中（验收误判） | 验收口径必须**分层披露**：① 显式 `l4_eligible=True` 的子集（当前语料 **0 条**，需先造）② 27 条缺省可进 L4 的子集 ③ 全语料；不得只报全语料 Δ=0 |
| R-6 | 与 T19 的 `category=="contract"` 耦合：若 lens 未真正产出 `contract` 类 finding，通道仍休眠 | 高 | 中 | T20 的验收必须包含**一条端到端 golden case**（lens 产物 → verify → contract 裁决），否则只算"schema 就绪"不算"激活" |

## 6. 实施建议（供 Step 3 设计 spec 采用或否决）

| # | 建议 | 依据 |
|---|---|---|
| S-1 | **规范字段名沿用 `category`**（已有 5 值枚举），**不引入新名**；`dimension` 保留为**正交的自由字符串**，不互转 | F-4 / X-5 / 只增不删 |
| S-2 | **新增 `schemas/sast-finding.schema.json`**：`category` 可选（枚举同源）、`dimension`/`l4_eligible`/工具元数据合法、`evidence` 允许 `cwe`/`owasp`/`rule_id`/`source` | 方案 B |
| S-3 | **映射表**（配置化，非硬编码 if-else）：Semgrep `metadata.category` → 内部 `category` 的**保守子集**；CodeQL `properties.tags` 含 `security` → 同；**无法映射 ⇒ 省略字段** | X-2 / X-4 / R-1 |
| S-4 | **`analysis_kind` 仅在工具确实给出数据流证据时写**（Semgrep 有 `dataflow_trace` / CodeQL 有 `codeFlows`），否则省略 | X-3 / R-4 |
| S-5 | 新增 **`scripts/validate_findings.py`**（纯 stdlib，零新增依赖）：按 schema 校验必填/枚举/类型，作为 CI 门与转换器自检 | ADR-023 / R-2 |
| S-6 | 修 `issues_tracker.py` 的 `finding["category"]` 强取 ⇒ `.get()` + `unknown` 桶；`inter_rater.py` 同步把 `unknown` 显式上报而非静默 | F-3 |
| S-7 | 验收必须给**两个触发面数字**：① semgrep/codeql（`l4_eligible=True`）子集；② 全语料。并给出**端到端 golden case**（R-6） | R-5 / R-6 |

**明确不做**：

- 不回溯改写 882 条既有语料（避免污染 T19/T9' 已冻结的 A/B 基线）；
- 不让转换器编造 `spec_ref` / `confidence` / `fix_cost`；
- 不引入 `jsonschema` 等第三方依赖（ADR-023）；
- 不把 `dimension` 改名为 `category`（一词两义会破坏既有守卫 `guards.yml` 的 `audit_lens` 语义）。
