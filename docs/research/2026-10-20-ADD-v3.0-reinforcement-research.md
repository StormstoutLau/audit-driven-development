## 1. 执行摘要

上一轮评估给出的五项短板中，**四项存在可借鉴的开源现成方案，一项（学习闭环）ADD 反而领先于同级项目**。

| 短板 | 一句话结论 |
|---|---|
| **W1 能力完备度**（Tier 2 仅 Python、无跨文件、taint 粗粒度） | 不存在「纯 stdlib + 跨过程 taint」的现成引擎；可行路线是**仿 Pysa 的声明式 taint model 自建策略层**，外加 **PyCG/Scalpel 式纯 Python 调用图**补跨函数 |
| **W2 实证强度**（N=202、无外部复现） | 提样本量成本最低的是 **ARVO + CWE-Bench-Java**；零门槛 ground truth 是 **OWASP Benchmark / Juliet**；`Alibaba-Aone/aacr-bench` 提供了「第三方语料 + 多人交叉标注」的**方法论范本** |
| **W3 外部有效性**（无 CI/IDE 分发、无规则生态） | `open-code-review` 是**同赛道分发能力的完整参照物**：npm CLI + GitHub Action + 6 个 agent 插件 + VSCode + 多平台 CI + MCP server。ADD 最该补的是 **SARIF 输出**（ADD 只消费 SARIF，不产出）与 **path-scoped 规则文件 + `rules check` 预览命令** |
| **W4 学习闭环半闭环** | CodeRabbit 的 `learnings`（从被忽略评论沉淀规则）是「半闭环→闭环」的商业实现；`open-code-review` 把「领域长期记忆」明确排到 H1 2027 —— **说明 ADD 的 hallucination_log→rule_suggestions 链路方向正确且领先**，缺的是让 `history_threshold` 真正改变验证行为 |
| **W5 文档漂移 / 自审计冻结** | `open-code-review` 的 **`ASSURANCE_CASE.md`** 范式是最佳借用对象：威胁模型 + 信任边界 + Saltzer&Schroeder 原则映射 + OWASP/CWE 对策表（逐条标 Mitigated/N-A）+ 自动验证表。**它是「持续维护的断言 + 证据指针」，天然抗漂移**，直接可替换 ADD 那个冻结在 v2.3 的 `97/100 A+` |

**优先级建议（工作量：S ≈ 数小时，M ≈ 数天，L ≈ 周级）**

| 序 | 动作 | 修复短板 | 工作量 |
|---|---|---|---|
| **1** | 产出 `ASSURANCE_CASE.md`（照抄 OCR 的章节结构，内容换为 ADD 自身） | W5 | **S** |
| **2** | ADD 增加 `--format sarif` 输出 + GitHub Action 包装 | W3 | **M** |
| **3** | 换用 ARVO / CWE-Bench-Java / OWASP Benchmark 重建 benchmark，公开复现脚本 | W2 | **M** |
| **4** | 把 `guards.yml` 落地为 path-scoped 规则文件 + 解析优先级链 + 预览命令 | W1 / W3 | **M** |
| **5** | 仿 Pysa 声明式 sources/sinks 定义 + PyCG 式 Python 调用图 | W1 | **L** |
| **6** | 治理补件：GOVERNANCE / CODE_OF_CONDUCT / i18n / OpenSSF 徽章 | W3 | **S** |

> **关键判断**：`open-code-review` **不能整体吸收**，但它是**分发工程与「持续断言式文档」的双重范本**。它的定位是「AI 代码评审器」（detection-side），与 ADD 的「SAST 验证层」正交互补，不构成替代。

**第二轮补强（§12–§14，v1.2 新增）**：第一轮覆盖「评审器 / 分析引擎 / 语料」，第二轮转向 ADD 的**确定性缺口与合规缺口**，并新增 **3 项 P0**：

| 第二轮新增 P0 | 一句话 |
|---|---|
| **#12 `import-linter`** | 用 INI `layers` 契约把「跨模块契约」从**概率性 LLM 透镜**转为**确定性规则**（纯 Python，不新增 runtime 依赖）—— 这是 ADD 头号护城河的确定性化 |
| **#13 OpenSSF Scorecard** | 比手写 assurance case **更自动**：每次仓库变更重扫 + 自动徽章，直接消解「97/100 算完没人再算」 |
| **#14 GitHub Code Scanning `upload-sarif`** | 与 #2 是**同一个动作**的下半段：#2 让 ADD 产出 SARIF，#14 给出接入的最小四条条件 |

另有一项**合规前置**结论：**Semgrep「引擎 ≠ 规则」** —— 引擎 LGPL-2.1 可自由使用，但**规则仅限内部使用、禁再分发** ⇒ ADD 若要分发规则，须改走 **Opengrep 引擎 + 自研规则**（详见 §14.1）。

### 3.2 核心设计哲学：确定性工程 × Agent 混合

OCR 明确把评审流程切成两半（本机 `README.md`「Core Design」节）：

- **确定性工程（硬约束）** —— 承担「绝不能出错」的步骤：精确文件选择、智能文件打包（相关文件并为一个评审单元，每个 bundle 以隔离子上下文并发运行）、**模板引擎驱动的细粒度规则匹配**、以及**独立的外部定位模块与反思模块**。
- **Agent（动态决策）** —— 只承担需要动态判断的部分：场景化 prompt、场景化工具集。

> **对 ADD 的直接映射**：ADD 的 4-Level 验证门本质上**就是**这套哲学的一个实例（L1/L2 是确定性门，L3/L4 是半确定性判断），但 ADD 从未把「哪些步骤必须由工程逻辑保证、哪些可交给模型」**显式形式化**。OCR 的表述可直接借用为 ADD 的架构陈述，并把 ADD 现有的确定性程度（文件存在/行号范围/关键词窗口）与需要模型判断的部分（claim 类型归类、结构性裁决）分开写清。

其中「**独立的定位模块 + 反思模块**」与 ADD 的 L2/L3 门是同一问题的两种实现：OCR 用独立模块修正「位置漂移」，ADD 用 L1/L2 把漂移的 finding 直接降为 `unverified`。**OCR 的「反思模块」思路（对每条意见再走一遍判断、不达标则丢弃）等价于 ADD 缺失的一环：ADD 有事后 L1–L4 裁定，但没有「先打分、低于阈值即静默丢弃」的前置门**（PR-Agent 的实现见 §4.2）。

### 3.3 可借用项一：path-scoped 规则文件 + 解析优先级链 + 预览命令

`.opencodereview/rule.json` 实测结构：

```json
{
  "rules": [
    {
      "path": "internal/llm/providers.go",
      "rule": "<自由文本：MUST/NOT 条款 + 文档同步要求 + 测试覆盖要求>",
      "merge_system_rule": true
    }
  ]
}
```

配套机制（实测于 `skills/open-code-review/SKILL.md`「Custom Review Rules」节）：

| 机制 | 说明 |
|---|---|
| **解析优先级链** | `--rule <path>` > `<repo>/.opencodereview/rule.json` > `~/.opencodereview/rule.json` > 内置系统默认 |
| **合并语义** | 默认「首个命中用户规则**替换**内置系统规则」；置 `merge_system_rule: true` 时二者**同时生效** |
| **路径匹配** | 支持 gitignore 风格 glob（`**/*.java`、`**/*mapper*.xml`） |
| **预览命令** | `ocr rules check <file>` —— **在评审前先看哪个规则会命中该文件** |

> **对 ADD 的映射**：ADD 的 `docs/audit/guards.template.yml` / `guards.common.yml`（P3.1/P3.3）与之**目标完全重合但落地更弱** —— ADD 有 guard 概念却**没有解析优先级链、没有合并语义、没有预览命令**，而这三样恰是让「人类写规则、AI 查合规」在真实项目中可用的关键。**该机制是本次调研中投入产出比最高的可移植项之一**：ADD 的 guard 体系可直接补上 `--guards` 参数优先级、`extends` 合并语义（P3.3 已设计）与 `guards check <file>` 预览。

### 3.4 可借用项二：SARIF 输出与分发矩阵

OCR 的输出面（实测 `skills/open-code-review/SKILL.md`「Advanced Review Options → Output」）：

- `--format text|json|**sarif**`，其中 sarif 明示用于「code-scanning integrations such as GitHub Code Scanning」
- `--audience agent`（抑制进度 UI，只输出最终摘要，供宿主 agent 消费）
- `--output <path>` + `--resume <id>`（大评审的防截断与断点续跑）
- `--preview`（只列出将要评审的文件，不调 LLM）
- `--max-tokens-budget`（总量预算，超预算的文件标记为 `failed(budget)`）

**ADD 的现状是单向管道**：消费 Semgrep/CodeQL 的 SARIF，但**不产出 SARIF**。这意味着 ADD 验证后的 findings **无法回流到 GitHub Code Scanning / reviewdog** 这类已有的呈现与门禁基建 —— 这是 W3「无 CI 分发」最便宜的一个缺口。补上 `--format sarif` 后，ADD 即可作为 Code Scanning 的上游步骤接入 GitHub Actions。

OCR 的分发矩阵（实测目录 + README）覆盖：

```
npm CLI  ─┬─ GitHub Action (action.yml 55 KB)
          ├─ Claude Code 插件 (.claude-plugin/plugin.json + commands/review.md)
          ├─ Codex 插件 (.codex-plugin/plugin.json)
          ├─ Cursor 插件 (.cursor-plugin/plugin.json)
          ├─ Kimi Code 插件 (commands/review.md)
          ├─ OpenCode 插件 (TypeScript)
          ├─ 通用 skill (skills/open-code-review/SKILL.md)
          ├─ VSCode 扩展 (Roadmap 已交付)
          ├─ CI: GitHub Actions / GitLab CI / GitFlic / Gerrit
          ├─ MCP server (可被任意 MCP 客户端调用)
          └─ ACP stdio adapter (H2 2026 实验性)
```

> **对照 ADD**：ADD 已有 `adapters/`（`AGENTS.md`×2、`SKILL.md`、`audit-driven-development.mdc`、`copilot-instructions.md`、`.windsurfrules`），**在「指令文件适配」这一层覆盖面甚至更广**（含 Windsurf/Copilot）。ADD 缺的不是适配文件，而是**可执行载体**：没有 npm/二进制分发、没有编辑器扩展、没有 CI action、没有 MCP server。

### 3.5 可借用项三：`ASSURANCE_CASE.md` —— 抗漂移的「持续断言」

`ASSURANCE_CASE.md`（本机实测，11 KB）的章节结构：

| 章节 | 内容 | 为什么对 ADD 关键 |
|---|---|---|
| **Threat Model** | 系统描述 / 参与者信任级别表 / 信任边界图 / 威胁汇总表（T1–T7，每条含 ID·威胁·边界·缓解） | 把「系统可能怎么坏」显式化，而非散落在 ADR 里 |
| **Secure Design Principles** | 把 Saltzer & Schroeder 八原则**逐条映射到本项目的具体实现** | 断言必须落到实现证据，不能只喊口号 |
| **Countermeasures Against Common Weaknesses** | OWASP Top 10 (2021) + CWE Top 25 **逐条**给出 Applicability 与 Countermeasure，结论列**只能是 Mitigated / Not applicable** | 每条风险**必须**有一个判定，无法含糊带过 |
| **Automated Verification** | 检查项 → 工具 → 触发时机表（`go vet` / `govulncheck` / `go test -race` / Dependabot / `go.sum`） | **每条断言绑定一个可执行的 CI 检查** |

> **为什么这是 W5 的最优解**：ADD 目前用 `docs/audit/scores.json` + 「自审计评分 97/100 A+」表达质量，而该评分**冻结在 2026-07-12（v2.3 时代）**，v2.4→v3.0 六个版本从未重跑。一次性评分的结构性缺陷是：**分算出来之后没人会再算一次**。Assurance Case 的形态恰好相反 —— 它是**逐条断言**，每条断言绑定一个缓解措施和一个自动检查；**一旦代码变化导致某条断言不再成立，检查会先失败**，而不是等下一次「重新审计」。ADD 的 ADR-026/027、4-Level 门、kill switch、回归套件都可以直接改写进这张表。

### 3.6 可借用项四：Benchmark 方法论（AACR-Bench）

OCR 在 README 中公布 benchmark：**50 个开源仓库 / 200 个真实 PR / 10 种语言 / 1,505 条人工标注 ground-truth 问题 / 80+ 高级工程师交叉校验**，并已将数据集发布到 HuggingFace（`Alibaba-Aone/aacr-bench`）。其自报结论为：同模型下 Precision 与 F1 显著高于通用 agent，token 消耗约为其 1/9，**Recall 更低且为「刻意以精度换噪声」的取舍**。

**对本项目最重要的一点不是数字，而是「同等取舍 + 公开语料 + 多人交叉标注」这套方法论** —— 它与 ADD 的定位高度同构：

- ADD 同样**主动牺牲 recall 换 precision**（P0 100% 通过门、L4 证伪即降级）；
- ADD 的 benchmark 是**自建自标**（687 条中仅 202 条可验证，标注无第三方交叉校验）；
- ADD 目前**没有公开发布的数据集**。

> **注意适用边界**：AACR-Bench 标注的是「代码评审意见的真伪」，**不是**「SAST finding 的真伪」，因此**不能直接拿来当 ADD 的评测集**，只能作为**方法论模板**（第三方语料、多人交叉标注、公开发布、指标口径固定为 P/R/F1/耗时/token）。

### 3.7 反向发现：ADD 在「学习闭环」上领先于本项目

`ROADMAP.md`（实测）把 **H1 2027** 的目标定为：

> **Domain-Specific Long-Term Memory** —— Persistent review knowledge: enable the review engine to accumulate domain-specific knowledge over time (recurring patterns, past review decisions, project-specific conventions) and apply it to future reviews, **improving relevance and reducing repeated feedback**.

这正是 ADD **已经部分建成**的 `hallucination_log → rule_suggestions → classify_claim` 链路与 `fix_history` 奖励信号。同时 `ROADMAP.md` 的 **Not Planned** 节明确排除了「自动修复」「通用编码助手」「自托管 LLM」，即本项目**刻意不做**闭环的自动修复端。

| 维度 | ADD（现状） | open-code-review（规划） |
|---|---|---|
| 幻觉/误报沉淀 | ✅ 已建（`hallucination_log` + 反例规则） | ⏳ 计划 H1 2027 |
| 规则反馈到识别 | ⚠️ 半闭环（`history_threshold` 写入 finding 但不驱动验证） | ⏳ 未规划 |
| 优化目标措辞 | 「自演化规则」 | **「reduce repeated feedback」** —— 更可度量的目标函数，值得借用其措辞与度量方式 |

> **结论**：在「让审计器随时间变聪明」这一轴上，ADD 是**领先方**。补强方案不应照抄本项目，而应**借其度量口径**（「重复反馈减少率」）把 ADD 的半闭环补完。

## 4. 案例二：AI 代码评审类开源工具

2. **误报抑制已有两个成熟范式可直接吸收**：reviewdog 的「只报变更行」（≈ADD L2）+ PR-Agent 的「反思打分 + 阈值丢弃」（≈ADD L3/L4 的前置版）。二者都证明：**把验证门放在「过滤」而非「解释」位置，是可行且被生产验证的**。
3. **「忽略即学习」是半闭环补全的最短路径**：CodeRabbit `learnings` 把「用户忽略了一条评论」当作负样本信号。ADD 的 `hallucination_log` 目前只在**验证失败**时记录，**未把「人工最终否决」纳入** —— 这是 W4 最便宜的一个增量。
4. **无一个开源项目公布了可独立复现的 precision/recall 评测**；厂商对比数字均为自报或二级来源。这说明「可复现评测」在 AI 评审赛道**普遍缺失**，是 ADD 可以建立差异化的位置。

## 5. 案例三：程序分析引擎类

| 工具 | 许可 | 语言 | 分析深度 | 需可构建? | 输出 | 纯 Python 3.9 stdlib 可调用? |
|---|---|---|---|---|---|---|
| **Pysa**（Meta） | MIT | Python | **跨过程 taint** | 否 | JSON | ✗ 依赖 OCaml/Pyre 工具链 |
| **Infer**（Meta） | MIT | Java/C/C++/ObjC | 跨过程（分离逻辑/Pulse） | **是**（capture build） | JSON / **SARIF** | ✗ 需 JVM + clang |
| **CrossHair** | MIT | Python | 符号执行（契约级） | 否（读源码） | 反例文本 | 半：需 z3 二进制 |
| **icontract / deal** | MIT | Python | 运行时契约 | 需可运行 | 异常 | **✓ 纯 Python** |
| **KLEE** | UIUC/NCSA | C | 动态符号执行 | **是**（→LLVM bitcode） | 自有格式 | ✗ |
| **Frama-C** | LGPL | C | 抽象解释 / 演绎验证 | 否（自带 parser） | 自有格式 + ACSL | ✗ |
| **WALA** | EPL-2.0 `[unverified]` | Java 字节码/JS | 跨过程切片/指针分析 | **是** | Java API | ✗ 需 JVM |
| **Soot / FlowDroid** | LGPL-2.1 | Java/Android | 跨过程 taint | **是** | XML/Jimple | ✗ 需 JVM |
| **CodeQL** | 引擎专有 / 查询库 MIT | 多语言 | 全局跨过程 taint | **是** | **SARIF** | ✗ |
| **Semgrep CE / Opengrep** | LGPL-2.1 | 多语言 | 同文件跨函数 taint | 否（tree-sitter） | SARIF/JSON | 半：CLI 二进制 |
| **Bearer** | ELv2（**非 OSI**） | Java/Py/JS/Go | 规则 + 流（跨文件限 Pro） | 否 | SARIF/JSON | 半：CLI 二进制 |
| **PyCG / Scalpel** | Apache-2.0 / `[unverified]` | Python | 调用图 / CFG+DFG（**无 taint**） | 否 | JSON | **✓ 纯 Python 库** |

**Takeaway**

1. **没有单一开源引擎能同时满足 ADD 的四项约束**（纯 Python 3.9 stdlib、无需构建、跨过程、结构化输出）。这是**结构性事实**，不是工具选型问题 —— 意味着「跨文件验证」只能靠**组合**（自建策略层 + 可 Python 调用的调用图库 + 可选外部 CLI），不能靠引入一个引擎解决。
2. **Pysa 是唯一开源、跨过程、Python taint 的引擎**，但其运行在 **Pyre（OCaml）** 之上，需 opam 构建；且无法解析 import 的历史代码会失效 —— **与 ADD「处理不可构建历史代码」的定位直接冲突**，只能作为可选的外部 Tier 补充，不能作为主力。
3. **需可构建代码的分析器（Infer / CodeQL / Soot / FlowDroid / WALA / KLEE）应明确排除为主力**，仅对可编译子集启用。这实际上**反向确认了 ADD 的定位取舍是正确的**：它换取的正是「不可构建代码也能验证」这一能力。
4. **`SARIF` 是可行的统一消费层**：Infer、CodeQL、Bearer、Semgrep/Opengrep 均原生产出 SARIF，Pysa 产出 JSON。ADD 应加一层 SARIF/JSON 适配器，以 subprocess 调 CLI —— **与 §3.4 的「ADD 自身也产出 SARIF」形成双向接口**。
5. **最佳增量路径是「借范本、不借引擎」**：
   - 仿 **Pysa 的声明式 taint model**（用配置文件定义 sources/sinks，而非硬编码正则），设计 ADD 的策略层；
   - 用 **PyCG / Scalpel 式纯 Python 调用图**补跨函数（零依赖、无需构建，正好落在 ADD 的约束内）；
   - 用 **Frama-C 的 ACSL 契约**作为结构性验证的规范表述范本。

### 6.2 评测方法论（学术界口径）

主流口径是 **OWASP Benchmark 评分法**：由 TP/FP/TN/FN 导出 **TPR / FPR / Youden 指数**，见 *ARES'22*「A Quantitative Assessment of the Detection Performance of Web Vulnerability Scanners」（doi `10.1145/3538969.3544416`）。2025 年的系统基准（arXiv `2508.04448`）与 ZeroFalse（arXiv `2510.02534`）同样以 OWASP Java Benchmark / 真实项目报 precision/recall/F1。语料质量的批评见 *ICSE'23*「Data Quality for Software Vulnerability Datasets」（arXiv `2301.05456`）。

### 6.3 规则生态

| 生态 | 规则量 | 许可 | 机器可读 / 导出 |
|---|---|---|---|
| **Semgrep Registry** | **3,000+** 社区规则 | **引擎 = LGPL-2.1**（可自由使用/修改/商用）；**规则 = Semgrep Rules License v1.0**（2024-12 起：**仅限内部、非竞争、非 SaaS 用途；禁再分发、禁作为服务对外提供**，须保留声明） | YAML → SARIF/JSON/CSV |
| **Opengrep**（Semgrep CE 社区 fork） | fork 自 CE v1.100.0（约 2025-01） | **引擎 LGPL-2.1 且语法兼容 CE** ⇒ 合规替代引擎；其规则仓 `opengrep-rules` 为 **LGPL-2.1 + Commons Clause**（仅禁售卖/托管，比 v1.0 宽松）但**更新停滞** `[unverified]` | SARIF/JSON |
| **CodeQL** | 默认 **496** 安全查询（169 CWE）+ 131 扩展 ≈ **627** | 按用户专有许可（公开仓库免费） | `.ql` 源码 + SARIF |
| **SonarSource** | **6,000+**（5,300 唯一质量+安全） | 源可见 **SSAL-1.0**（限用） | 规则元数据 API / SARIF |
| **OWASP ASVS** | 5.0.0 需求条目 ID | CC BY-SA 4.0 | JSON/CSV |
| **CWE Top 25** | 25 项 | 免费（MITRE） | CSV/XML |

**Takeaway**

1. **提样本量首选 ARVO**（5,001 条有 patch、可重建，最贴「finding 真伪」判定）；**CWE-Bench-Java**（120 条人工核验）虽小但标签质量最高，适合作**高置信锚点**；DiverseVul / PrimeVul 提供函数级 pairwise 标签，成本中等。
2. **零集成门槛的 ground truth 是 OWASP Benchmark 与 Juliet/SARD** —— 有逐例预期结果、可直接算 TPR/FPR/Youden，适合作为「永不过拟合的固定哨兵集」；但因其**合成**，只能作辅助，不能单独支撑泛化声明。
3. **Big-Vul / CVEfixes 不宜继续作为评测集**：标签噪声（约 25% 正确）、高重复率、时序泄漏问题在研究界已有定论（arXiv `2301.05456`）。ADD 当前 610 条不可验证样本正是其后果 —— **继续扩大该语料只会放大噪声，不会增加证据**。
4. **「引擎 ≠ 规则」是本轮最重要的许可结论**：Semgrep **引擎** LGPL-2.1 可自由使用/修改/商用，但 Semgrep **维护的规则**采用 **Semgrep Rules License v1.0 —— 仅限内部、非竞争、非 SaaS 用途，且禁再分发、禁作为服务对外提供**（须保留声明）⇒ ADD **可内部消费、不可再分发**；若需合法的可再分发规则源，须改为 **Opengrep 引擎（LGPL-2.1，语法兼容 CE）+ 自养/自研规则（Apache-2.0）**。余下风险点：Sonar 为 SSAL-1.0、Bearer 为 ELv2（**非 OSI**，禁做托管服务）—— **任何「规则再分发 / 打包进 ADD」的动作都必须先过许可，且需法务级确认**（本调研为工程检索，非法律意见）。

## 8. 明确排除项（不建议吸收）

| 排除对象 | 理由 |
|---|---|
| **把 OCR / PR-Agent 的 AI 评审引擎整体吸收** | 它们是 **detection-side 评审器**；ADD 的定位是 **verification layer**（ADR-001 / ADR-016）。自建 detection 违背既有决策，且会在 3000+ 规则的 Semgrep 面前无胜算 |
| **需可构建代码的分析器作为主力**（Infer / CodeQL / Soot / FlowDroid / WALA / KLEE） | 与 ADD「可验证不可构建的历史代码」定位**直接冲突**，仅可对可编译子集择优启用 |
| **闭源 SaaS 作为依赖**（CodeRabbit / Corgea / Ellipsis / ZeroPath / Graphite） | ADD 为 MIT / 零依赖取向，引入闭源服务破坏可复现性 |
| **Big-Vul / CVEfixes 继续扩样本** | 标签噪声约 25% 正确率，扩大只会放大噪声（arXiv `2301.05456`） |
| **照抄 AACR-Bench 作为 ADD 评测集** | 其标注对象为「代码评审意见真伪」，与「SAST finding 真伪」口径不同 |
| **引入 ACP / 自建协议适配层** | OCR 的 ACP 适配器在其自身 Roadmap 中仍标 **experimental（仅本地源码构建）**；ADD 无此需求 |
| **Semgrep Registry 规则再分发** | 规则许可为 **Semgrep Rules License v1.0**：仅限内部、非竞争、非 SaaS，**禁再分发 / 禁作为服务对外提供**。合规路径是改用 **Opengrep 引擎 + 自养/自研规则** |
| **把 SLSA / in-toto / cosign 作为「第三方证据」主线** | 三者门槛均建立在**可发布产物**上；ADD 是无二进制产物的框架，收益低。要第三方背书应优先走 **OpenSSF Best Practices Badge**（silver 级主要补治理文件、2FA、≥2 贡献者） |
| **Bearer 作为托管/再分发组件** | 其许可为 **ELv2（非 OSI）**，**禁做托管服务**，仅可自用；作为 ADD 的规则分发载体不合规 |
| **Kyverno 用于 ADD 规则层** | 其 YAML+CEL 模型**仅面向 Kubernetes 资源**，与 ADD 的「代码/文件树合规」不匹配（可作 `guards.yml` 语法候选参考，不可作引擎） |

## 9. 结论

`open-code-review`（Apache-2.0，Go，阿里巴巴开源）是**分发工程与持续断言式文档的双重范本**，但**不是可吸收的引擎**。它的价值集中在三处：

1. **`ASSURANCE_CASE.md` 范式** —— 直接修复 W5，且成本最低（一笔文档工程量）；
2. **SARIF 输出 + 完整分发矩阵** —— 直接指向 W3 最便宜的缺口；
3. **path-scoped 规则文件 + 优先级链 + 预览命令** —— 把 ADD 已有但悬空的 `guards` 体系落到可用。

程序分析引擎方向的调研给出一个**否定性但重要**的结论：**不存在同时满足「纯 stdlib + 无需构建 + 跨过程」的现成引擎**。这反向确认了 ADD 的定位取舍是**结构性正确**的 —— 它换取的能力（不可构建代码也能验证）恰是前沿工具都不提供的那一格。跨文件能力因此只能靠**自建策略层 + 纯 Python 调用图**逐步补齐。

Benchmark 方向的调研给出了**最直接的证据升级路径**：ARVO + CWE-Bench-Java + OWASP Benchmark 三件套可把可验证样本从 N=202 抬到 N≫1000，并同时获得可复现评测口径。

最后一处**反向发现**值得记录：在学习闭环这一轴上，ADD 领先于本次调研的全部对象 —— `open-code-review` 把「领域长期记忆」排到 H1 2027，CodeRabbit 只做到「忽略即学习」。ADD 的欠账不是「没有闭环」，而是**闭环未闭合到「驱动验证行为」**（`history_threshold` 写入但不生效），以及**负样本来源过窄**（只有验证失败，没有人工否决）。

### 9.1 第二轮补强给出的三条新结论（v1.2）

1. **ADD 的头号护城河目前建在概率性地基上**。它自称最独有的能力是「Spec↔Code 契约对齐」，但承担该能力的 7 个透镜是 **LLM 判断**。第二轮找到了**纯 Python、零新依赖**的确定性替代：**`import-linter` 的 `layers` 契约**可以显式表达「高层不得依赖低层」并**检出间接依赖**。把这一层从「透镜」改造成「规则」，是本次调研**投入产出比最高的单项**（§7 #12，P0）。
2. **「持续」优于「一次性」这一条被第二次证实**。第一轮发现 ADD 的 `97/100 A+` 冻结在 v2.3；第二轮找到了比手写 assurance case **更自动**的解法 —— **OpenSSF Scorecard**（每次变更重扫 + 自动徽章 + SARIF 输出）。结论应修正为：**Scorecard 管持续基线，assurance case 管本项目特有断言，两者并用**（§7 #13，P0）。
3. **SARIF 是本次调研中最具网络效应的单一接口**。`scorecard-action`、`reviewdog`、`upload-sarif`、`sarif-tools`、以及全部聚合器（Trivy / Grype / Checkov / KICS / datadog-static-analyzer）共同收敛到 **SARIF 2.1.0**。ADD **产出**一份合规 SARIF 即可同时接入「徽章 / PR 评论 / Code Scanning / 趋势对比」四个消费面 —— 这是 W3 的最小充分动作（与 §7 #2、#14 合为一个动作）。

**另有一条合规层面的硬约束需要前置处理**：**Semgrep 的「引擎 ≠ 规则」**。引擎 LGPL-2.1 可自由使用；但 Semgrep 维护的规则采用 **Semgrep Rules License v1.0 —— 仅限内部、非竞争、非 SaaS，且禁再分发、禁作为服务对外提供**。⇒ **ADD 可以内部消费 Semgrep 规则，但一旦要随项目分发，必须改为 Opengrep 引擎 + 自研规则**（§14.1 / §8）。这一条不解决，任何「规则生态」类补强都会带着法律风险。

## 12. 第二轮调研：契约不变量、策略即代码与发现管理

> 第二轮补足了第一轮未覆盖的三个方向。第一轮偏重「评审器 / 分析引擎 / 语料」，本轮转向 ADD 的**确定性缺口**：它自称的头号护城河「Spec↔Code 契约对齐」目前由 **LLM 透镜（概率性）** 承担，而这一层其实有成熟的确定性开源实现。

| 工具 | 许可 | 语言 | 机制（一句话） | 纯 Python 3.9 可调用 | 最值得借鉴的一点 |
|---|---|---|---|---|---|
| **`import-linter`** | BSD-2 | Python | INI 契约，`type=layers` 声明「高层不得依赖低层」（含**间接依赖**检测） | ✅ 库 / CLI（新版需 ≥3.10，可 pin 旧版） | **声明式分层契约 + 间接依赖检测** ⇒ 直接可替 LLM 透镜 |
| **ArchUnit** | Apache-2.0 | Java | 导入字节码，用测试断言依赖/分层/切片约束 | subprocess + JVM | `layer().definedBy()` 的分层单向依赖建模 |
| **dependency-cruiser** | MIT | JS | 配置 `forbidden[{from,to,severity}]` 做正/负路径正则 | subprocess | **正/负路径 forbidden 规则**表达 |

| **Dredd** | MIT | JS | 按 spec 回放请求、比对响应 | subprocess | 「以 spec 为真源**逐条回放**」 |
| **Schemathesis** | MIT | Python | schema → Hypothesis 属性测试 | subprocess（需 ≥3.10） | 由 schema **生成**测试而非只校验 |
| **Spectral** | Apache-2.0 | JS | ruleset lint 任意 JSON/YAML | subprocess | 通用 lint 引擎 + 自定义 ruleset |

| **OWASP DefectDojo** | BSD-3 | Python | 4 种去重算法 + FP 生命周期跟踪 | REST / CLI | `HASHCODE_FIELDS_PER_SCANNER` + **FP History 自动回标** |
| **Faraday** | GPL-3 | Python | 归一化 90+ 工具 findings | REST / CLI | 多格式摄取归一化 |

**Takeaway**

1. **第 1 组五款全部能用声明式表达「A 不得依赖 B / 分层不得反向」**。范本首选 **`import-linter`**：纯 Python、INI `layers` 契约显式区分「高→低可依赖、反向禁止」，且**能检出间接依赖** —— 这正是把 ADD 的「跨模块契约」透镜从概率性转为确定性所需的最小件，**且不引入新 runtime 依赖**（落在 ADR-023 约束内）。
2. **Pact 的双向机制可解 ADD 的单向困境**：ADD 目前只做「spec → 代码」的检查；Pact 的「消费者断言 + 提供者回放」启发把 spec 拆为**「期望断言（规则引擎确定性执行）」+「代码侧回放兜底」**两层，前者替掉 LLM 透镜，后者保留语义判断。
3. **spec 校验宜分层**：结构用 **JSON Schema**（库内调用，零成本）、风格/语义用 **Spectral ruleset**、运行时用 **Dredd / Schemathesis** —— 三者皆确定性、皆可 subprocess。
4. **Rego 适配 `guards.yml` 但有一个硬前提**：`guards` 的键值语义天然对得上 Rego 的 JSON 断言模型，`Conftest` 是它的 CLI 封装且可 `--output=json`；**但 Rego 不解析源码**，ADD 必须先把「文件树 / 代码结构」抽象为 JSON 输入。若嫌 Rego 重，**Kyverno 的 YAML+CEL 是更轻的语法候选**（但引擎本身不可用，因它只面向 K8s）。
5. **DefectDojo 是 ADD 状态机的对齐范本**：`verified_findings` / `hallucination_log` / `issues.json` 目前缺三样 —— **可配置哈希去重字段**、**「同资产最早创建者为 original」的归并规则**、**FP 的跨轮历史回标**。DefectDojo 的 `HASHCODE_FIELDS_PER_SCANNER` 与 FP History 恰好给出了这三样的成熟设计。

| **OWASP Threat Dragon** | Apache-2.0 | ❌ 桌面/Web | 一次性图 | 规则引擎自动生成威胁+对策，可导出存档 |
| **SACM**（OMG 元模型，非工具） | 规范公开 | ❌ | — | **Claim–Argument–Evidence 三层**可直接映射 ADD 的断言结构 |
| **MADR** | MIT OR CC0-1.0 | ❌（模板） | — | **`Confirmation` 段**：明确「如何确认实现是否符合本决策」⇒ **天生可转 CI 校验** |
| **adr-tools** | MIT | ✅ | 一次性（生成/编号） | 编号 + 目录 + superseded 链，文件即真相 |
| **log4brains** | Apache-2.0 | ✅ npm | **持续：站点随分支自动重建** | 文档随代码分支**自动更新** ⇒ 直接治「漂移」 |
| **AdrGuard**（.NET） | `[unverified]` | ✅（稳定退出码 ADR001–009、JSON/SARIF） | 持续 | **ADR ↔ 代码映射 + 漂移校验**，用退出码变成 **CI 硬门** |
| **Archgate** | `[unverified]`（商业） | ✅ `archgate check` | 持续（棘轮：失误→新规则） | 每条 ADR = **人读文档 + 机器可校验规则** 双表达 |
| **`sarif-tools`** | MIT | ✅ pip | 持续 | Python 汇总 / **diff SARIF**，做趋势对比 |
| **`reviewdog`** | MIT | ✅ | 持续 | `-f=sarif` ⇒ 结果变 PR 行内评论 |
| **`github/codeql-action/upload-sarif`** | MIT | ✅ | 持续 | **最小接入条件**（见下方 callout） |

> **GitHub Code Scanning 最小接入条件（实测口径）**：`SARIF **2.1.0**` + workflow 声明 `permissions: security-events: write` + **每个 result 必须带 `ruleId`**（须先定义 rules 数组）+ 单文件 **≤10 MB**。满足这四条，ADD 产出的 SARIF 即可复用整个 GitHub 安全生态（告警永久留存、可 diff、可复算）。

**Takeaway**

1. **比「手写 assurance case」更优的选项已经存在**：**Scorecard 是持续门禁**（每次变更重扫 + 自动徽章），assurance case 仍需人工维护。建议**两者并用**——Scorecard 管「仓库健康度的持续基线」，assurance case 管「本项目特有的威胁与对策断言」。
2. **最低成本主线**：借 **MADR `Confirmation` 段** + **AdrGuard/Archgate 思路**，**给 ADD 现有 27 条 ADR 各配一条机器可校验规则**，再用 `upload-sarif` 把审计产物变成 GitHub Code Scanning 告警 —— 这条链把「ADR 是否落地」从文档承诺变成 **CI 硬门**。
3. **威胁建模选 `pytm` / `Threagile`，不选 Threat Dragon**：只有前两者能把「威胁 + 对策 + 验证」存成**可重复生成的结构化文件**，可 diff、可入 CI。
4. **SLSA / in-toto / cosign 对 ADD 收益低**：三者门槛均建立在**可发布产物**上。要第三方背书，优先走 **CII Best Practices Badge（silver 级主要补治理文件、2FA、≥2 贡献者）**，而非自建签名链。
5. **SARIF 是全链路的公共接口**：`scorecard-action`、`reviewdog`、`upload-sarif`、`sarif-tools` 共同收敛到 **SARIF 2.1.0**。ADD 只要产出 SARIF，就能同时接入「徽章 / PR 评论 / Code Scanning / 趋势对比」四个消费面 —— 这使 §7 中 #2 与 #14 成为**同一个动作**。

### 14.3 修复基准（给 Repair 轨道一个可复现指标）

| 基准 | 规模 | 备注 |
|---|---|---|
| **SWE-bench Verified** | **500** 实例（人工核验 Python） | 官方 harness **MIT** ⇒ **最低成本路径** |
| SWE-bench（原版） | 2,294 实例 | — |
| **SWE-Gym** | 2,438 实例，含**可执行环境** | 训练 + 评测 |
| **R2E-Gym** | **8.1K** 程序化任务，含混合 verifier | — |
| **Vul4J** | 79 漏洞 / 51 项目 / 25 CWE | Java 可复现漏洞 |

修复工具（择要）：**AutoCodeRover**（仓库许可 `[unverified]`）、**SWE-agent** MIT、**OpenHands** MIT、**RepairLLaMA**、**VulMaster**、**LLM4Vuln**、**Vul-RAG**。

**Takeaway**

1. **「引擎 ≠ 规则」是本轮最重要的许可结论**：Semgrep CE 引擎 LGPL-2.1 可自由使用，但 **Semgrep 维护的规则** 采用 **Semgrep Rules License v1.0 —— 仅限内部、非竞争、非 SaaS，且禁再分发、禁作为服务对外提供**。⇒ ADD **可内部消费、不可再分发**；要合法的可再分发规则源，必须改为 **Opengrep 引擎 + 自养/自研规则（Apache-2.0）**。
2. **Opengrep 是唯一的合规替代引擎，但其规则仓也不干净且停更**：`opengrep-rules` 仍是 **LGPL-2.1 + Commons Clause**（禁售卖/托管，比 v1.0 宽松），且据二手来源已停更 `[unverified]` ⇒ **规则必须自养或自研**。
3. **幻觉锚点首选 `CodeHaluEval`**（8 类幻觉分类学 + 8,883 样本 + 公开数据），辅以 HalluCode、Collu-Bench —— 这给 `hallucination_log` 提供了**可引用的字段口径**，使 ADD 的「幻觉」概念从自造词变成学术可对接的概念（`Collu-Bench` 还覆盖了自动程序修复场景，与 ADD 的 Repair 轨道同域）。
4. **Repair 轨道的最低成本指标路径**：接 **SWE-bench Verified 官方 harness** 得 **pass@1**（harness 为 MIT，复现成本最低）；Java 侧补 **Vul4J**。在没有这一步之前，ADD 的 Repair 轨道**没有任何可验证的质量声明**。
5. **聚合器全线 Apache-2.0 且原生输出 SARIF**（Trivy / Grype / Checkov / KICS / datadog-static-analyzer）⇒ 可直接喂给 ADD 作为**额外的 findings 来源**；唯一例外是 **Bearer（ELv2，非 OSI，禁做托管服务）**，仅可自用。
