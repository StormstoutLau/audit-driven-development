## 10. 经验教训

1. **Spec 驱动开发的自我应用**：本次审计用 ADD 框架自身的 L1-L4 验证逻辑审计 spec 文档，验证了"方法论发明家"的核心能力——验证基础设施能验证自身的设计文档
2. **行号精确性是幻觉排除的关键**：C1-C5 的验证全部依赖行号精确匹配，如果 spec 中行号错误，L2 会立即捕获。这证明了 verify_findings L2 级别的价值
3. **L4 结构验证的不可替代性**：C7-C8（调用关系/消费关系）无法用 L1-L3 验证，必须 grep 全目录。这正是 Phase 8 修复 Joern CPG + ast CFG 的动机——结构化验证比正则更可靠
4. **Spec 本身可能成为幻觉源**：如果不审计 spec，设计文档中的错误行号、不存在的文件引用、虚构的调用关系会进入实施阶段。Phase 8 的 3 个 FP 根因之一（ground truth 错误）就是未审计的"spec"
