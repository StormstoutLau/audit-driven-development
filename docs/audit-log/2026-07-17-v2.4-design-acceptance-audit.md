### P1-2: CFG Try/Except 中 return 后 except 不可达

**位置**: [Plan §A.2.1 `visit_Try`](file:///f:/Coding/audit-driven-development/docs/superpowers/plans/2026-07-17-v2.4-joern-cpg-implementation.md)

**问题**: `visit_Return` 清空 `_current_successors = []`。在 `visit_Try` 中，如果 try 体内有 return:

```python
def foo():
    try:
        return 1      # ← visit_Return 清空 _current_successors
        x = 2         # ← dead code (正确)
    except:
        handle()      # ← Plan 逻辑: try_successors 为空 → except 分支不可达
```

**实际语义**: `except` 分支在 try 体抛异常时仍然可达，即使 try 体有 return。return 只清空 try 体内部的后续语句可达性，不应影响 except 分支。

**修复**: `visit_Try` 中 except 分支应从 try 入口（而非 try 体出口）连接:

```python
def visit_Try(self, node):
    try_line = node.lineno
    self._add_node(try_line, "Try")
    self._connect_predecessors(try_line)

    # try 体
    self._current_successors = [try_line]  # 从 try 入口开始
    for stmt in node.body:
        self.visit(stmt)
    try_successors = self._current_successors[:]

    # except 分支: 从 try_line 连接 (不是从 try_successors)
    all_branch_exits = try_successors[:]
    for handler in node.handlers:
        handler_line = handler.lineno
        self._add_node(handler_line, "ExceptHandler")
        self.edges.append((try_line, handler_line))  # ← 从 try 入口连接
        # ... (不从 try_successors 连接)
```

**验证**: 需要增加 TDD 测试用例:
```python
def test_except_reachable_after_return_in_try(self):
    """try 体有 return, except 分支仍应可达"""
    code = textwrap.dedent('''
        def foo():
            try:
                return 1
            except:
                handle()
    ''')
    result = verify_dead_code_in_source(code, line=4)
    assert result["verified"] is False  # except 不是 dead code
```

### P2-4: `visit_While = visit_For` 别名问题

**位置**: [Plan §A.2.1](file:///f:/Coding/audit-driven-development/docs/superpowers/plans/2026-07-17-v2.4-joern-cpg-implementation.md)

**问题**: `visit_While = visit_For` 直接别名。但 Python 中:
- `for` 的 else 子句在循环正常结束（非 break）时执行
- `while` 的 else 子句在条件变为 False 时执行
- 两者 CFG 结构相同（循环头 → 循环体 → back edge + 循环出口 → else），但 else 的语义触发条件不同

**评估**: 对于 dead_code 验证（可达性分析），else 子句的触发条件不影响可达性 — else 分支从循环出口可达。因此别名在 CFG 层面是正确的。

**修复**: 增加注释说明别名合理性:
```python
# While 与 For 的 CFG 结构相同 (循环头→体→back edge+出口→else)
# else 的触发条件不同 (for: 正常结束; while: 条件False) 但不影响可达性分析
visit_While = visit_For
```

## 9. 算法正确性手动 Trace

### 9.1 CFG 构建 Trace — if/else 分支

**输入代码**:
```python
def foo(cond):
    if cond:        # line 2
        x = 1       # line 3
    else:
        y = 2       # line 5
    return x if cond else y  # line 6
```

**期望 CFG**:
```
entry(1) → if(2) → then: assign(3) → merge → return(6)
                 → else: assign(5) → merge ↗
```

**Trace `visit_If`**:
1. `visit_FunctionDef`: `_current_successors = [1]`
2. `visit_If`: cond_line=2, `_connect_predecessors(2)` → edges: [(1,2)]
3. then 分支: `_current_successors = [2]`, visit `x=1` (line 3) → `_current_successors = [3]`
4. then_successors = [3]
5. else 分支: `_current_successors = [2]`, visit `y=2` (line 5) → `_current_successors = [5]`
6. else_successors = [5]
7. 合并: `_current_successors = [3, 5]`
8. `visit_Return` (line 6): `_connect_predecessors(6)` → edges: [(3,6), (5,6)]

**结果**: ✅ 正确。line 3 和 line 5 都可达，line 6 从两者可达。

### 9.2 BFS 可达性 Trace

**CFG**: nodes={1,2,3,5,6}, edges=[(1,2),(2,3),(2,5),(3,6),(5,6)]

**查询**: `is_reachable(nodes, edges, entry=1, target=3)`

**Trace**:
1. adjacency = {1:[2], 2:[3,5], 3:[6], 5:[6], 6:[]}
2. visited={1}, queue=deque([1])
3. pop 1 → neighbors=[2] → 2 not visited → visited={1,2}, queue=deque([2])
4. pop 2 → neighbors=[3,5] → 3==target → return True

**结果**: ✅ 正确。

### 9.3 三色 DFS 环检测 Trace

**图**: a→b, b→c, c→a (有环)

**Trace**:
1. start_node=a, color[a]=GRAY, stack=[(a,0)]
2. pop (a,0): neighbors=[b], stack[-1]=(a,1), neighbor=b, color[b]=WHITE → color[b]=GRAY, parent[b]=a, stack=[(a,1),(b,0)]
3. pop (b,0): neighbors=[c], stack[-1]=(b,1), neighbor=c, color[c]=WHITE → color[c]=GRAY, parent[c]=b, stack=[(a,1),(b,1),(c,0)]
4. pop (c,0): neighbors=[a], stack[-1]=(c,1), neighbor=a, color[a]=GRAY → **找到环!**
5. 回溯: cycle=[a], current=c → cycle=[a,c], current=b → cycle=[a,c,b], current=a → stop
6. cycle.reverse() → [b,c,a] → 等等，reverse 后是 [b,c,a,a]?

**问题发现**: 环路径回溯逻辑有 bug!

```python
cycle = [neighbor]  # [a]
current = node      # c
while current != neighbor and current is not None:
    cycle.append(current)  # [a, c, b]
    current = parent.get(current)  # parent[c]=b, parent[b]=a
cycle.append(neighbor)  # [a, c, b, a] ← 重复了 a
cycle.reverse()  # [a, b, c, a]
```

**实际输出**: `["a", "b", "c", "a"]` — 正确的环路径 (a→b→c→a)。

**修正**: 上面 trace 的 step 5 计算有误。重新 trace:
- cycle = [a], current = c
- c != a → cycle = [a, c], current = parent[c] = b
- b != a → cycle = [a, c, b], current = parent[b] = a
- a == a → stop
- cycle.append(a) → [a, c, b, a]
- reverse → [a, b, c, a]

**结果**: ✅ 正确。环路径 `a → b → c → a`。

## 14. Lessons Learned / 经验教训

- **Spec 与 Plan 的缓存策略不一致** (P1-1) 暴露了 Spec→Plan 翻译过程中的信息丢失。建议在 Plan 的工程决策表中显式标注"与 Spec §X 的差异"。
- **CFG Try/Except 语义错误** (P1-2) 是算法设计中的典型陷阱——return 的终止效应不应跨 try/except 边界传播。手动 trace 发现了这个问题，说明算法 trace 是不可省略的验收步骤。
- **字段名不统一** (`verified` vs `confirmed`) (P0-2) 是多模块集成时的常见问题。建议在 Spec 中定义统一的返回值 schema，所有 Tier 遵循同一 schema。
- **Joern Scala DSL 的概念性代码** (P1-5, 原 P0-1) 被误标为 Blocker。设计文档中的概念性伪代码应标注为 "pseudo-code"，严重度应为 P1 (实施前实测) 而非 P0 (阻断设计)。
- **审计文档自身产生幻觉** (P1-3 误报 + P0-1/P1-4 过度升级) 是元层面的教训。审计者在未完整阅读 Plan §A.4 的情况下声称 `context_text` 未定义 (P1-3), 以及将代码正确的 P1-4 标为 Critical、将概念性伪代码 P0-1 标为 Blocker。**源码级追溯是审计自身的必要约束** — 这正是 Phase 3.5 存在的根本理由, 也是本次修复首先执行源码级追溯的动机。
