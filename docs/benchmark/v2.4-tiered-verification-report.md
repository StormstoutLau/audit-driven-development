# ADD v2.4 三层降级验证框架 — 代码审计测试报告

**测试日期**: 2026-08-05
**框架版本**: v2.4 (Phase 2.4a + 2.4b complete)
**测试范围**: 3 个代码库 (1 本地 + 2 开源)，共 27 个合成 finding

---

## 1. 测试目标

验证 ADD v2.4 Phase 3.5 三层降级验证架构（Tier 1: Joern CPG → Tier 2: Python ast CFG → Tier 3: regex）在真实代码审计场景下的表现：
- **准确率 (Precision)**: 不会把真实 bug 误判为幻觉（FP=0 是硬性要求）
- **召回率 (Recall)**: 能识别多少合成幻觉
- **Tier 降级链路**: Tier 1→2→3 是否按预期触发
- **L1-L4 分层验证**: 文件存在、行号有效性、关键词匹配、结构化验证

## 4. 分层验证触发分析

### 4.1 L1 (文件存在性) — 100% 有效

| 项目 | 触发次数 | 结果 |
|---|---|---|
| ADD self-audit | 0 | (所有 finding 文件均存在) |
| Python stdlib | 1 (OSS-H1) | ✓ 正确移除 (nonexistent_file.py) |
| itsdangerous | 1 (ITD-H1) | ✓ 正确移除 (nonexistent_module.py) |

**结论**: L1 对"幻觉文件"检测完美，零误报。

### 4.2 L2 (行号有效性) — 100% 有效

| 项目 | 触发次数 | 结果 |
|---|---|---|
| ADD self-audit | 0 | (所有行号均有效) |
| Python stdlib | 1 (OSS-H2) | ✓ 正确移除 (line 9999 > 357) |
| itsdangerous | 1 (ITD-H2) | ✓ 正确移除 (line 9999 > 267) |

**结论**: L2 对"越界行号"检测完美。

### 4.3 L3 (关键词匹配 ±20 行) — 高效但有局限

| 项目 | 触发次数 | 移除 | 误报 |
|---|---|---|---|
| ADD self-audit | 1 (SA-6) | 1 | 0 |
| Python stdlib | 1 (OSS-H8) | 1 | 0 |
| itsdangerous | 2 (ITD-H4, ITD-H6) | 2 | 0 |

**结论**: L3 在关键词无法匹配时能有效移除幻觉。但对关键词恰好匹配的幻觉（如 OSS-H3 "dead code" 关键词出现在上下文中）无法识别。

### 4.4 L4 Tier 2 (Python ast CFG) — 结构化验证核心

| Finding | Claim Type | Tier 2 结果 | 是否正确 |
|---|---|---|---|
| SA-1 (dead_code) | dead_code | verified=False (reachable) | ✓ 正确降级 |
| SA-3 (circular dep) | import_related | verified=False (no cycle) | ✓ 正确降级 |
| OSS-H3 (dead_code) | dead_code | (未触发降级) | ✗ 假阳性 |
| OSS-H4 (dead_code) | dead_code | verified=False (reachable) | ✓ 正确降级 |
| OSS-H5 (circular dep) | import_related | verified=True (found OTHER cycle) | ✗ 假阳性 |
| OSS-R1 (import exists) | import_related | verified=True (found cycle) | ✗ 语义不匹配 |
| ITD-H3 (dead_code) | dead_code | verified=False (reachable) | ✓ 正确降级 |
| ITD-R1 (import exists) | import_related | verified=False (no cycle) | ✗ 语义不匹配 |

**关键发现**:
1. **dead_code 检测准确** — Tier 2 ast CFG 通过 BFS 可达性分析，正确识别了 3/4 的"可达代码被声称死代码"幻觉
2. **import_related 语义错位** — `verify_imports()` 检测的是"是否存在任何循环依赖"，而 claim 可能是"A 和 B 之间有循环依赖"（特定模块对）。当项目中存在其他循环时（如 stdlib 的 abc→_py_abc→...），会产生假阳性

### 4.5 L4 Tier 1 (Joern CPG) — 未触发

所有测试均在 Windows 主控站运行，Joern CLI 部署在 WSL2 Ubuntu-24.04 中。`joern_cpg.is_available()` 在 Windows Python 环境下返回 False，自动降级到 Tier 2。

**验证方式**: 通过 `test_v24_consistency.py` 中的 mock 测试 (J1-J10) 验证 Tier 1 接口正确性，V9 异常路径测试验证降级链路。

### 4.6 L4 Tier 3 (regex fallback) — 兜底但粗糙

| Claim Type | 触发次数 | 准确率 |
|---|---|---|
| missing | 2 | 50% (1 正确降级，1 假阳性) |
| wrong | 2 | 100% (均正确移除) |
| violates | 1 | 100% (正确降级) |
| generic | 2 | 100% (均正确验证) |

**结论**: Tier 3 作为最后兜底，对 "missing" 类 claim 准确率较低（regex 难以判断"缺失"是否真实），但对 "wrong"/"generic" 类表现可接受。

## 5. 关键发现与局限

### 5.1 优势 ✓

1. **零误报 (FP=0)** — 最重要的指标，3 个测试中从未将真实 bug 误判为幻觉。这保证了审计基线不会因框架错误而丢失真实发现。

2. **L1+L2 基础验证可靠** — 文件存在性和行号有效性检查 100% 准确，能捕获最粗糙的幻觉（编造文件、编造行号）

3. **Tier 2 ast CFG 对 dead_code 检测有效** — BFS 可达性分析在 3 个项目中均正确识别了"可达代码被声称死代码"的幻觉（SA-1, OSS-H4, ITD-H3），降级为 P1 供人工复核。

4. **Tier 降级链路工作正常** — Tier 1 不可用时自动降级到 Tier 2，Tier 2 无法判定时降级到 Tier 3，全程无崩溃。

### 5.2 局限 ✗

1. **Recall 偏低 (42.1%)** — 多数幻觉仅被降级而非移除。原因：L3 关键词匹配过于宽松（只要上下文 ±20 行内有关键词就通过），L4 Tier 3 regex 对 "missing" 类 claim 无法准确判断。

2. **import_related 语义错位** — `verify_imports()` 检测"是否存在任何循环依赖"，但 claim 可能指定特定模块对（"A 和 B 之间"）。导致：
   - 假阳性：项目有其他循环时，错误验证特定循环 claim (OSS-H5)
   - 假阴性：无循环时，错误否定"import 存在"claim (ITD-R1)

3. **Tier 1 (Joern CPG) 未在 Windows 环境触发** — `joern_cpg.is_available()` 检测 WSL2 路径，但 Windows Python 无法直接调用 WSL2 中的 Joern CLI。需要通过 WSL2 运行整个 ADD 流水线才能启用 Tier 1。

4. **P1 finding 仅做 L1+L2 轻量验证** — P1 finding 不触发 L4 结构化验证，导致 P1 级别的幻觉（如 SA-5, SA-8, OSS-H7）无法被检测。

### 5.3 改进方向

| 优先级 | 改进项 | 预期效果 |
|---|---|---|
| P1 | `verify_imports()` 支持解析 claim 中的模块对，验证特定循环而非任意循环 | 消除 import_related 假阳性/假阴性 |
| P2 | L3 关键词匹配增加"反向验证"（如 claim 说 "missing X"，则检查 X 是否真的缺失） | 提升 missing 类 Recall |
| P2 | P1 finding 可选触发 L4（当 finding 数量较少时） | 提升 P1 幻觉检测 |
| P3 | Windows 环境通过 subprocess 调用 WSL2 中的 Joern CLI | 启用 Tier 1 |
| P3 | L4 增加 "raise_statement" claim type（检测 raise 是否存在） | 覆盖更多结构化 claim |

---

## 6. 测试结论

**ADD v2.4 三层降级验证框架在 Precision 维度满足生产要求 (100%)，在 Recall 维度有明确改进空间 (42.1%)。**

框架的核心价值在于**保护审计基线不被幻觉污染**：FP=0 意味着所有被移除的 finding 确实是幻觉，不会丢失真实 bug。Recall 偏低意味着部分幻觉会进入降级 (P1) 状态，但降级后的 finding 仍需人工复核，因此不会直接产生错误修复。

**推荐使用场景**:
- ✓ 生产环境：作为 P0 finding 的"幻觉过滤器"，确保进入修复基线的 P0 finding 经过源码级验证
- ✓ 团队协作：降级到 P1 的 finding 作为人工复核清单
- ⚠ 自动化流水线：Recall 42.1% 意味着约 58% 的幻觉需要人工判断，不适合完全自动化

**下一步**: 实施 P1 改进项（`verify_imports()` 模块对解析），预期可将 Recall 提升至 60%+。
