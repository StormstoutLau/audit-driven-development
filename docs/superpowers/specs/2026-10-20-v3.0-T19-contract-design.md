## 0. 背景与问题陈述

### 0.1 要修复的短板

W1：ADD 自称最独有的护城河是「Spec↔Code 契约对齐」，但该能力由 **7 个 LLM 透镜**承担（概率性判断）。**跨模块契约类断言没有任何确定性验证** —— `classify_claim` 无 `contract` 类型（[verify_findings.py L197-206](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L197-L206)，L229 回落 `["generic"]`），`verify_l4_structural` 仅对 `dead_code` 与 `import_related`（[L511-516](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L511-L516)）做结构化验证，generic 门条件（[L541](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L541)）中不含 contract ⇒ 该类 finding 一律落到 **Tier 3 正则**。

### 0.2 战略定位约束

```
T19 = 验证 contract 断言（复核「A 依赖 B / 分层被违反」这类断言的成立与否）
T19 ≠ 检测契约违反（不新建一个「扫全仓找分层违规」的引擎）
```

据此，T19 的输入是**已存在的 finding**（由透镜/Subagent 产出，`category: "contract"`），输出是**对该断言的验证裁决**。ADD 的 pipeline 定位（ADR-001：SAST Findings Validator / verification-first）不变。

### 0.3 本步解决的三个设计缺口

| # | 缺口 | 代码/实测证据 | 影响 |
|---|------|--------------|------|
| **GAP-1** | **claim 类型体系无 contract** | [L197-206](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L197-L206)：`missing / wrong / violates / dead_code / import_related` + `taint` | 契约断言无法进入任何结构化分支 |
| **GAP-2** | **`guards.yml` 是半死文件**：无消费者、`check` 是自由文本 | [merge_guards.py L22-33](file:///f:/Coding/audit-driven-development/scripts/merge_guards.py#L22-L33)（仅按 id 合并）· [spec_graph.py L144-167](file:///f:/Coding/audit-driven-development/scripts/spec_graph.py#L144-L167)（仅解析 scope glob）；`docs/audit/` 下**只有** `guards.common.yml` / `guards.learned.yml` / `guards.template.yml`，**`guards.yml` 不存在** | 人类写的规则**无法被机械执行** —— 「人写规则、AI 查合规」（P3.1 原始设计）只完成了一半 |

### 0.4 事实核验（外部 + 本机实测）

| 事实 | 结论 | 来源 |
|------|------|------|
| import-linter `layers` 语义 | ✅ 有序层列表；`layers[i]` 可依赖 `layers[j]`（j>i），反向禁止；**间接依赖同样违规** | [import-linter 文档](https://import-linter.readthedocs.io/)（T1） |
| import-linter 可作为依赖引入？ | ❌ **不可** —— [ADR-023](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L525-L542)「标准库优先，不引入新 runtime 依赖」**无例外条款**，且明确排除过 JVM 依赖与 `sarif-tools` | ADR-023 原文 |
| `ast_cfg.build_import_graph` 可直接复用？ | ⚠️ **构建可用，作用域敏感** —— 见 GAP-3 / F-1 | 本机实测 |
| 结构化通道（`category` / `analysis_kind`）在当前语料上可达？ | ❌ **0 命中** —— 882 条语料**整体不含 `category` 字段**（F-3） | 本机实测 |
| 文本通道的初始正则是否有效？ | ❌ **4/882 且全为噪声**（`msPostGISLayerSetTimeFilter` 命中 `layers?`）⇒ 必须收紧（X-2） | 本机实测（F-4） |
| `category: "contract"` 有无真实生产者？ | ✅ 有 —— 透镜产物经 `ModuleAuditResult` 携带该字段 | [test_v25 L54](file:///f:/Coding/audit-driven-development/scripts/test_v25_consistency.py#L54) · [test_v35 L60](file:///f:/Coding/audit-driven-development/scripts/test_v35_consistency.py#L60) |

**核验结论**：T19 的**结构化通道在生产链路可达、在当前 benchmark 语料不可达**（与 taint 通道 A 完全同型）。故 MVP 必须（a）**不依赖语料**即可被验证 —— 由**合成 repo 夹具**与**真实 repo 用例**承担；（b）按 taint AC-8 模式**显式披露休眠**。

## 1. 设计决策

> 每条含：决策 / 理由 / 后果 / 追溯。

### D-T19-1: 新增 claim 类型 `contract_related`（双通道识别）

- **决策**: `classify_claim` 新增 `contract_related` 标签，命中以下**任一**通道（**仅当 `_contract_enabled()` 为真**）：
  - **通道 A（结构化，两条承载路径）**:
    - `category == "contract"` —— **经新增可选参数传入**（见下方「接口变更」，H5 修正）
    - `evidence.analysis_kind == "contract"` —— 经 `evidence` 传入（对齐 taint 的结构化通道写法，[L211](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L211)）
  - **通道 B（文本，兜底）**: 模块级预编译 `CONTRACT_PATTERNS` 命中 claim 文本
- **理由**: GAP-1。双通道设计直接复用 taint 的成功模式（D-T9'-1）；`category` 是透镜产物的既有字段，**实现成本为零**。
- **接口变更（H5 修正，**本 spec 唯一的签名变更**）**: `category` 是 finding 的**顶层字段**，而 `classify_claim(claim, evidence=None)`（[L177](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L177)）与其**唯一调用点** `classify_claim(claim, evidence)`（[L970](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L970)）**均不接收该字段** ⇒ 若不修改，通道 A 的 `category` 判据**永远不可达**，AC-2 不可能通过。
  ⇒ 修正：`classify_claim` 新增**可选**参数 `category=None`（**只增不删，向后兼容**；默认 `None` 时行为与现状完全一致），调用点 L970 改为 `classify_claim(claim, evidence, finding.get("category"))`。
- **文本通道正则的实证收紧（X-2）**: **禁用裸 `layers?` 与裸 `contract`**（F-4 实测二者在 882 条真实语料上仅产生噪声，命中 `LayerSetTimeFilter` 等标识符子串）。定稿模式为**带词边界的中英短语集**（非穷举）：`\blayer violation\b` · `\blayering\b` · `\bcross-module dependency\b` · `\barchitectural boundary\b` · `层序` · `分层契约` · `反向依赖` · `禁止依赖` · `跨模块依赖`
- **理由（为何不用更宽的正则）**: 沿用 taint 教训 —— 「关键词命中估计若使用比最终实现更宽松的正则，会系统性偏高」。此处反向：**更宽的正则产生的是假阳性**，会污染 benchmark。
- **不变式**: `contract_related` 与既有类型**叠加不互斥**（`classify_claim` 本就是多标签语义）。
- **追溯**: 调研 §4 F-3/F-4 · [T9' 设计 spec D-T9'-1](file:///f:/Coding/audit-driven-development/docs/superpowers/specs/2026-10-20-v3.0-T9prime-taint-design.md)

### D-T19-2: 契约声明扩展 `guards.yml`（只增不删）

- **决策**: 在 guard 条目内新增**可选** `contract` 子对象；**既有 `id` / `description` / `scope` / `severity` / `check` 五字段一律不动**。无 `contract` 字段的 guard 仍是纯 AI 约束。

```yaml
guards:
  - id: "G101"
    description: "scripts/ 生产链单向依赖：上层可依赖下层，反向禁止"
    scope: "scripts/**/*.py"          # 保留：人读标注 + 候选集（可复用 resolve_guard_scopes）
    severity: "critical"              # 保留：缺省严重度（blocker→P0 / critical→P1 / warning→P2 / info→P3）
    check: "..."                      # 保留：自由文本，给 AI 用，本步不消费
    contract:                         # ★ 新增，可选
      root: "scripts"                 # ★ 图根（相对 repo 根）；默认 "." —— 见 D-T19-3 / F-1
      kind: "layers"                  # 当前唯一取值（预留扩展）
      layers: ["run_phase8_benchmark", "verify_findings", "joern_cpg", "ast_cfg", "_script_utils"]
      allow: []                       # 可选：**反向例外白名单**（见下）—— ADD 自身用例无反向例外，故为空
```

- **`root` 字段是本步的实证修正 X-1**：F-1 证明 `build_import_graph` 对图根敏感（仓库根调用得 0 边且**静默**）。缺省 `"."`（repo 根），ADD 自身用例显式写 `"scripts"`。
- **层序语义**: `layers[i]` **可**依赖 `layers[j]`（j>i）；`j<i` 即违规。与 import-linter `layers` 一致但**自实现**。
- **`allow` 语义（H1 修正）**: `allow` 是**反向例外白名单** —— 显式允许**特定的「低→高」边**（即对层序禁令的例外）。`allow: [["X","Y"]]` 表示「尽管层序禁止 X→Y，此处例外允许」。
  > v1.0 曾把 `allow` 定义为「**高→低**白名单」，但层序**本身已允许**高→低 ⇒ 该白名单对任何边都不产生约束力，**语义为空**（Step 4 审计 H1）。真实构造示例：若某项目确需允许 `["ast_cfg", "verify_findings"]`（低→高），才写进 `allow`。
- **间接依赖**: 图上**存在**从高到低的传递路径即违规（非仅直连边）。
- **层↔模块映射**: `layers[k]` 作为**模块名前缀**匹配。
- **未命中任何层的模块 ⇒ 忽略（非违规）**：分层是**声明范围内的偏序**，不构成全库约束。
- **加载路径探测顺序**: `docs/audit/guards.yml` → `guards.project.yml` → `guards.common.yml` → **无 ⇒ `None`**。
- **后果**: guards schema 只增；旧文件（无 `contract`）解析不报错；`merge_guards.py` / `spec_graph.py` **不改**（它们按字段名访问，新增字段天然透传）。
- **追溯**: 调研 GAP-2 / F-1 · [guards.template.yml L5](file:///f:/Coding/audit-driven-development/docs/audit/guards.template.yml#L5)

### D-T19-3: Tier 2 纯 stdlib 契约求值（复用导入图，不引入 import-linter 依赖）

- **决策**:
  1. 契约求值走 **Tier 2**（纯 stdlib），复用 `ast_cfg.build_import_graph`（[L400-442](file:///f:/Coding/audit-driven-development/scripts/ast_cfg.py#L400-L442)）与 `_parse_modules_from_claim`（[L456-506](file:///f:/Coding/audit-driven-development/scripts/ast_cfg.py#L456-L506)）。
  2. **import-linter 仅作语义范本，不作为依赖引入**（ADR-023 无例外条款，**因此本步不需要修订 ADR-023**）。
  3. 新增能力放**独立模块** `scripts/contract_graph.py`，**不改 `ast_cfg.py`** —— 后者是 `test_v24` 等既有套件的被测对象，避免触碰高回归风险文件。

- **后果**: `Tier` 数值仍在 `{1,2,3}`；本能力**不占用 Tier 1**（Tier 1 仍为 Joern 专属）。
- **追溯**: 调研 §3 · ADR-023 · 补强报告 §12

### D-T19-4: 三态裁决 + **图完整性哨兵**（None 优先，绝不假 False）

- **决策**: 裁决三态语义如下（给定「claim 中解析出的模块 + 方向」× 「声明的 layers 契约」× 「实际导入图」）：

| 状态 | 成立条件 | 后果 |
|---|---|---|
| **`verified=True`** | 声明合法 ∧ 相关模块均在图中 ∧ 图**通过完整性哨兵** ∧ **claim 断言的不良依赖确实存在**（图上存在被禁方向/层序违规路径，且不命中 `allow`） | `tier=2`，结构化确认 |
| **`verified=False`** | 同上 ∧ **断言的依赖不存在，或存在但被 `allow` 豁免** | `tier=2`，结构化证伪 ⇒ 依 **ADR-018 移除**（`disproof_action` 默认 `remove`） |
| **`verified=None`** | **其余全部情形**（§2.3 列举） | **不写入该 check** ⇒ 回落 generic（Tier 3）⇒ 交既有路径裁决 |

- **图完整性哨兵（本步的新增硬要件，源自 F-1）**: 若 `图模块数 > 1 且 内部边数 == 0` ⇒ 判 `graph_incomplete` ⇒ **`None`**。理由：0 边图与「确实无依赖」数值同形，若不拦截将产生系统性**假 False**。
- **理由**: 沿用 taint 的教训（`sink_nodes == 0` 与"无路径"同形 ⇒ 必返回 `None`）。
- **后果**: 哨兵触发时契约分支**静默不生效**（不报错、不写 check），符合「永不崩溃」的既有降级纪律。
- **追溯**: 调研 §4 F-1（GAP-3）· [T9' 设计 spec D-T9'-3](file:///f:/Coding/audit-driven-development/docs/superpowers/specs/2026-10-20-v3.0-T9prime-taint-design.md)

## 2. 语义与接口

### 2.1 对外唯一入口

```
verify_contract(repo_root, claim, evidence=None, guards_path=None) -> dict | None
```

- `None` = 无裁决（调用方**不写 check**）。
- 非 `None` = 统一 schema（与既有 check 同构）：`{"verified": bool, "confirmed": bool, "tier": 2, "reason": str, "rule_id": str|None, "claim_types": list, ...}`。

### 2.2 claim → 模块与方向的提取（含未决 R-1 的收敛）

- 模块名：复用 `_parse_modules_from_claim`（[L456-506](file:///f:/Coding/audit-driven-development/scripts/ast_cfg.py#L456-L506)）。
- **方向判据（最小充分）**:
  | claim 形态 | 方向语义 | 处置 |
  |---|---|---|
  | `X imports Y` | 断言 **X → Y** | 按 X→Y 与层序比对 |
  | `X imports itself` | 断言自环 | **层次语义不适用 ⇒ `None`**（H4 修正：自环属**循环依赖**断言，不属**分层**断言；同层自环既非"高→低"也非"低→高"） |
  | `between X and Y` / `among ...` | **方向不可判定** | ⇒ **`None`**（不得猜测方向） |
- **模块数 < 1 或无方向 ⇒ `None`**。

### 2.3 `None` 的完整触发清单（**必须穷举，防漏**）

1. `guards.yml` 及其探测路径下**无任何含 `contract` 的声明**
2. YAML 解析失败 / 顶层结构非预期
3. 声明的 `layers` **非法**：为空、<2 项、含重复项、`kind != "layers"`
4. claim 中**提取不到模块**，或方向**不可判定**
5. 任一相关模块**不在图中**（含：模块名拼写、外部依赖、被跳过的语法错误文件）
6. **图完整性哨兵触发**（模块数 > 1 且内部边 == 0）
7. **动态 import** 命中（`__import__` / `importlib.import_module`）**于 `src`** ⇒ **仅把「被禁方向 + 无路径」这一支降为 `None`**（该支才可能被隐藏边伪造为 `False`）；**允许方向的 `False` 与已确认的 `True` 不受影响**（**Step 9 实施期细化**，见 [实施规范 §2.2 注](file:///f:/Coding/audit-driven-development/docs/superpowers/specs/2026-10-20-v3.0-T19-contract-implementation.md)）
8. **相对导入**无法解析
9. 图根不存在 / 不可遍历
