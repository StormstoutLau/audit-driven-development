## 1. 问题陈述

### 1.1 当前训练数据的局限

v2.5 闭环已通，但 `live_knowledge.py` 的所有学习脚本（`diff_miner` / `fix_history` / `rule_suggester`）只消费 ADD 自身审计产生的 `docs/audit/issues.json` 与 `hallucination_log.json`。这意味着：

| # | 局限 | 后果 |
|---|------|------|
| L1 | 27 个 ground-truth findings 全部来自 3 个被审计对象（ADD 自身 / Python stdlib / itsdangerous 2.2.0） | claim 类型分布偏斜：基于 3 个 benchmark 的 ground_truth.json 手动统计，`dead_code` 10 条 + `import_related` 5 条 = 15/27 (55.6%)，`wrong` 仅 3 条 (11.1%)，`violates` 为 0 条 (0%) |
| L2 | 真实 bug 仅来自 itsdangerous 与 stdlib 这种"小型纯 Python"项目 | 框架对大型多模块项目（django/flask 量级）的泛化能力未被验证 |
| L3 | 幻觉样本全部人工撰写（3 个 benchmark 目录的 `hallucination.json` 共 8 条被移除记录：[add-v2.4-self-audit/hallucination.json](file:///f:/Coding/audit-driven-development/docs/benchmark/add-v2.4-self-audit/hallucination.json) 1 条 + [stdlib-oss-test/hallucination.json](file:///f:/Coding/audit-driven-development/docs/benchmark/stdlib-oss-test/hallucination.json) 3 条 + [itsdangerous-2.2.0/hallucination.json](file:///f:/Coding/audit-driven-development/docs/benchmark/itsdangerous-2.2.0/hallucination.json) 4 条；`ground_truth.json` 中共 21 条 hallucination 标注），无规模化合成机制 | `rule_suggester` 的反例规则只能覆盖已知失败模式，新失败模式出现时无法快速学习 |
| L4 | benchmark recall 71.4% / F1 83.3% 长期停滞 | v2.5 rerun 与 v2.4-phase8 指标完全相同（[v2.5-benchmark-rerun.json](file:///f:/Coding/audit-driven-development/docs/benchmark/v2.5-benchmark-rerun.json#L242-L257)），说明闭环已通但学习信号不足 |

### 1.2 框架核心能力对数据的需求

ADD 的核心能力是 **claim ↔ source 对齐验证**：给定一条 finding（claim + evidence.file + evidence.line_start），通过 L1-L4 判定该 claim 是否被源码支持。要让这套能力"沉淀"，需要三类数据：

| 数据类型 | 用途 | 当前缺口 |
|----------|------|----------|
| **真实 bug 样本** | 提供 `real_bug` ground truth，校准 L4 结构验证 recall | L1 — 仅 27 个样本 |
| **幻觉样本** | 提供 `hallucination` ground truth，校准 L1-L3 precision | L3 — 仅人工 6 条 |
| **多 claim 类型分布** | 覆盖 `classify_claim()` 的 6 种输出（missing / wrong / violates / dead_code / import_related / generic），避免分类器偏斜 | L1 — `wrong` / `violates` 样本不足 |

### 1.3 目标

引入三层开源数据集，使框架具备：
1. **规模化真实 bug**：从 27 → ≥500 个 ground-truth findings
2. **自动化幻觉合成**：从人工 6 条 → 程序化生成（行号偏移 / 文件替换 / 方法虚构三类变换）
3. **claim 类型覆盖**：补齐 `wrong` / `violates` 类样本，使 6 种分类都有 ≥30 条样本

### 1.4 非目标

- **不**训练新的 ML 模型：本框架是规则 + 结构化验证系统，不引入神经网络分类器
- **不**改变 L1-L4 验证算法：数据集只填充 `findings.json` + `ground_truth.json`，验证逻辑保持 `verify_findings.py` 不变
- **不**替代现有 27 条 benchmark：保留为 smoke test，新增数据集作为扩展 benchmark
- **不**自动化 Java/C++ 的 L4 结构验证：Defects4J / Big-Vul / CVEfixes 数据先转换为统一 findings 格式，Java/C++ findings 暂只跑 L1-L3（文件存在性 + 行号有效性 + 关键词匹配），不依赖 Python `ast CFG` 或 Joern CPG（Java/C++ 的 L4 验证需后续版本集成 `javasrc2cpg` / `c2cpg` 前端）

## 2. 设计方案

### 2.1 数据集选型与三层架构

经 4 个候选数据集核查（核查证据见 §5 验收清单 D1-D4），选型如下：

```

│  ─────────────────────────────────────────────────────         │

│  语言: Python                                                  │
│  覆盖: 12 projects (django/flask/requests/sympy 等)             │
│  格式: issue description + gold patch + test cases             │

└────────────────────────────────────────────────────────────────┘
                              │

│                4249 projects, 11873 CVEs, 272 CWE types,       │
│                51342 files, 138974 functions                   │
```

**为何三层而非一层**：
- SWE-bench 是 Python 原生，与现有 `ast CFG` 验证链路零摩擦，但 issue 描述偏长，自然语言多，claim 提取需要 LLM
- Defects4J 提供 Java 行号精度，但需要 Joern CPG 支持 Java（Joern 官方支持 `javasrc2cpg` 前端，但 v2.4 仅集成了 Python 前端 `--language pythonsrc`，Java 前端需额外验证），且单 commit minimization 保证行号稳定
- Big-Vul + CVEfixes 提供 C/C++ 漏洞样本，CWE 类型丰富（272 种），但 C/C++ Joern 集成需额外验证

### 2.2 统一 findings 格式

所有数据集转换为 ADD 现有 [findings.json](file:///f:/Coding/audit-driven-development/docs/benchmark/add-v2.4-self-audit/findings.json#L1-L17) 格式：

```json
{
  "project": "<source_dataset>",
  "version": "<dataset_version>",
  "audit_date": "<conversion_date>",
  "audit_mode": "dataset-integration <layer>",
  "description": "<source description>",
  "findings": [
    {
      "id": "<DATASET_PREFIX>-<NNN>",
      "severity": "P0|P1",
      "claim": "<natural language claim derived from issue/CVE>",
      "evidence": {
        "file": "<relative path within repo>",
        "line_start": <int>
      },
      "dimension": "<one of: structural|error_handling|architecture|security|...>"
    }
  ]
}
```

**claim 生成策略**（按数据集）：
- SWE-bench: 直接取 `problem_statement` 前 200 字符 + 关键词提取（避免 LLM 引入二次幻觉）
- Defects4J: 取 fix commit message + 修改文件名 + 行号范围（无自然语言 issue 时回退到结构化模板）
- Big-Vul: 取 CVE summary + CWE 类型 → 模板化（如 `"function <name> has <CWE> vulnerability: <summary>"`)
- CVEfixes: 同 Big-Vul

### 2.3 阶段 1：SWE-bench 集成（Python 原生路径）

**目标**：将 SWE-bench Verified (500 条) 转换为 findings 格式，扩展 benchmark 至 ~500 条 Python 真实 bug。

#### 改动 1.1：新增 `scripts/swebench_to_findings.py`

**职责**：读取 SWE-bench JSONL，输出 findings.json + ground_truth.json

**输入**：SWE-bench Verified 子集（HuggingFace `princeton-nlp/SWE-bench_Verified`）

**输出**：
- `docs/benchmark/swebench-verified/findings.json` — 500 条 findings
- `docs/benchmark/swebench-verified/ground_truth.json` — 500 条 `real_bug` 标注

**核心逻辑**：
```python
def convert_swebench_instance(instance, idx):
    """Convert one SWE-bench instance to ADD finding format.

    SWE-bench instance fields (verified subset):
      - instance_id: e.g. "django__django-12345"
      - repo: e.g. "django/django"
      - base_commit: parent commit before fix
      - patch: gold patch (diff format)
      - problem_statement: issue description
      - FAIL_TO_PASS: tests that should pass after fix
    """
    # Extract file + line from patch
    file_path, line_start = extract_file_line_from_patch(instance["patch"])
    # Build claim from problem_statement (truncate to 200 chars, no LLM)
    claim = build_claim_from_issue(instance["problem_statement"])
    return {
        "id": f"SWB-{idx:04d}",
        "severity": "P1",  # SWE-bench bugs are real but not necessarily P0
        "claim": claim,
        "evidence": {"file": file_path, "line_start": line_start},
        "dimension": "functional"  # SWE-bench bugs are functional, not structural
    }
```

**patch 解析规则**（避免幻觉）：
- 只取 `+++ b/<path>` 行提取 file_path
- line_start 取第一个 `@@` hunk header 的 `-<start>,<count>` 中的 start
- 若 patch 为多文件，只取第一个文件（避免一条 finding 跨多文件）
- 若 patch 无法解析（罕见），跳过该 instance 并记录到 `conversion_errors.json`

**验收标准**：
- `python scripts/swebench_to_findings.py --input <swebench.jsonl> --output docs/benchmark/swebench-verified/` 执行后生成 findings.json + ground_truth.json
- findings 数量 = 500 ± 5（允许少量解析失败）
- 每条 finding 的 `evidence.file` 在 SWE-bench repo checkout 后存在
- 每条 finding 的 `evidence.line_start` ≥ 1

**当前**：`run_phase8_benchmark.py` 硬编码 3 个测试集（ADD self / stdlib / itsdangerous）。

**新增参数**：

### 2.4 阶段 2：幻觉样本自动合成

**目标**：从真实 bug 数据自动合成幻觉样本，扩展现有 6 条人工样本至 ≥100 条。

#### 改动 2.1：新增 `scripts/synthesize_hallucinations.py`

**核心思路**：对真实 bug 的 findings 施加 3 类变换，使其成为 hallucination ground truth。

```python
TRANSFORMS = {
    "line_offset": {
        "description": "将 line_start 偏移 ±N 行（N > 文件总行数 10%）",
        "ground_truth": "hallucination_line_out_of_range",
        "expected_l1_l2": "L2 line_out_of_range"
    },
    "file_replace": {
        "description": "将 evidence.file 替换为同 repo 内不存在路径",
        "ground_truth": "hallucination_file_not_found",
        "expected_l1_l2": "L1 file_not_found"
    },
    "method_fabricate": {
        "description": "在 claim 中插入 repo 内不存在的函数名",
        "ground_truth": "hallucination_method_not_in_source",
        "expected_l1_l2": "L3 no_keyword_match"
    }
}
```

**合成流程**：
1. 读取 `docs/benchmark/swebench-verified/findings.json`
2. 对每条 finding，随机选 1 种 transform（确保 3 类各占 ~1/3）
3. 输出 `docs/benchmark/swebench-verified-hallucinations/findings.json` + `ground_truth.json`

**验收标准**：
- 合成 findings 数量 = 真实 findings 数量（500:500 平衡）
- 每条合成 finding 的 `ground_truth` 标注为 `hallucination_*`
- 跑 `verify_findings.py` 后，≥90% 合成 finding 被正确识别为 hallucination（TP ≥ 450）
- 若 TP < 90%，触发 `rule_suggester` 生成新反例规则（v2.5 闭环已支持）

### 2.5 阶段 3：Defects4J + Big-Vul + CVEfixes 集成

**目标**：扩展到 Java 与 C/C++，补齐 `wrong` / `violates` 类样本。

#### 改动 3.1：新增 `scripts/defects4j_to_findings.py`

**输入**：Defects4J `active-bugs.csv` + 各 bug 的 fix commit diff

**输出**：`docs/benchmark/defects4j/findings.json` + `ground_truth.json`

**claim 生成模板**：
```python
DEFECTS4J_CLAIM_TEMPLATE = (
    "bug in {project_name} {file_path}:{line_start} — "
    "fix commit {commit_hash}: {commit_message}"

```

**约束**：
- 只取单文件 fix 的 bug（Defects4J 已 minimized，但部分 bug 仍跨多文件）
- 行号从 fix commit 的 diff 中提取
- 因 Joern CPG 对 Java 支持需额外验证，**阶段 3 的 Java findings 暂只跑 L1-L3**，不跑 L4 结构验证

#### 改动 3.2：新增 `scripts/bigvul_to_findings.py`

**输入**：`all_c_cpp_release2.0.csv`

**输出**：`docs/benchmark/bigvul/findings.json` + `ground_truth.json`

**claim 生成模板**：
```python
BIGVUL_CLAIM_TEMPLATE = (
    "function {func_name} has {cwe_id} vulnerability: {cve_summary} "
    "(CVSS {score:.1f}) — fix modifies lines {lines_before}"

```

**约束**：
- 只取 `vul == 1` 的函数（vulnerable functions）
- `func_name` 从 `func_before` 提取（首行函数签名）
- `line_start` 从 `lines_before` 提取（首个行号）
- 因 C/C++ Joern 集成需额外验证，**阶段 3 的 C/C++ findings 暂只跑 L1-L3**

## 3. 依赖关系与优先级

```
阶段 1 (SWE-bench) ──────► 阶段 2 (幻觉合成) ──────► 阶段 3 (多语言扩展)
  改动 1.1 + 1.2            改动 2.1 + 2.2            改动 3.1 + 3.2 + 3.3
  Python 原生路径            依赖阶段 1 的真实样本      Java/C/C++ 需 Joern
  必须先做                  作为合成源                验证（v2.4 已部分支持）
```

**阶段 1 是硬依赖**：幻觉合成需要真实 bug 作为种子，没有 SWE-bench 转换就无法规模化合成。

**阶段 2 可独立验收**：合成质量通过 `verify_findings.py` 的 TP 率直接衡量，不依赖阶段 3。

**阶段 3 可降级**：若 Joern Java/C++ 验证不通过，阶段 3 findings 仍可作为 L1-L3 benchmark 使用，不阻塞 v2.6 发布。

**优先级**：阶段 1 > 阶段 2 > 阶段 3。v2.6 发布只要求阶段 1+2 完成；阶段 3 作为 v2.6.1 增量。

## 4. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| SWE-bench patch 格式非标准（如 merge commit） | 中 | 中 | `extract_file_line_from_patch` 遇异常跳过，记录到 `conversion_errors.json`，不阻塞整体转换 |
| 合成幻觉样本的 TP 率 < 90% | 中 | 高 | 触发 `rule_suggester` 反例规则闭环（v2.5 已通），迭代至 TP ≥ 90% |
| Defects4J checkout 耗时长（864 bugs × Java 编译） | 高 | 中 | 阶段 3 只取 Top 50 bugs（每项目 ~3 个）作为试点，不全量转换 |
| Big-Vul CSV 解析内存峰值（C/C++ 函数体可能很大） | 中 | 中 | 用 `pandas.read_csv(chunksize=1000)` 流式读取，逐 chunk 转换 |
| CVEfixes SQLite 下载失败（Zenodo 网络问题） | 中 | 低 | 阶段 3 可选，失败时跳过 CVEfixes，仅用 Big-Vul |
| benchmark 全量跑耗时过长（500+ findings × L1-L4） | 高 | 中 | `run_phase8_benchmark.py` 新增 `--max-findings-per-test` 参数，默认 100，可调 |
| 新增 findings 导致 recall/precision 退化 | 中 | 高 | 阶段 2 完成后跑 `run_phase8_benchmark --baseline docs/benchmark/v2.5-benchmark-rerun.json`，触发 v2.5 的 regression check |
| Java/C++ findings 无法跑 L4（Joern 限制） | 高 | 中 | 阶段 3 findings 标注 `l4_eligible: false`，verify_findings 跳过 L4，不影响 L1-L3 指标 |
