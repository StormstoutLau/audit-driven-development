## 0. 背景与问题陈述

### 0.1 要修复的 Gap

G2 = ADD 无 taint 验证能力。SAST 工具（Semgrep / CodeQL）报告的 taint finding（source→sink 污点可达）无法被 ADD 的结构化验证门复核，只能落到 Tier 3 正则，导致该类别 finding 的假阳性无法被过滤。

代码证据：`Grep "taint|source|sink|flow"` 在 `scripts/` 下**代码层零命中**，`taint` 仅出现在 `docs/` 决策文档中。

### 0.2 战略定位约束（ADR-016）

```
T9' = 验证 taint（复核 SAST 报告的 source→sink 可达性）
T9' ≠ 检测 taint（不自建污点检测引擎）
```

因此 T9' 的输入是 **SAST finding**，输出是 **对该 finding taint 断言的验证裁决**，而非新的漏洞列表。

### 0.3 调研阶段暴露的三个设计缺口（本节是本 spec 的核心价值）

调研报告 §7.1 将"从 Semgrep/CodeQL finding 提取 source/sink"列为 MVP 范围，但**未定义提取机制**。经代码核对，发现三个必须在本步解决的事实缺口：

| # | 缺口 | 代码证据 | 影响 |
|---|------|---------|------|
| **GAP-1** | 两个 SAST 转换器**均未提取 taint 路径**，source 信息不存在 | [codeql_to_findings.py](file:///f:/Coding/audit-driven-development/scripts/codeql_to_findings.py#L104) 的 `convert_codeql_result` 只取 `locations[0]`（主位置 = query `select` 首列；CodeQL 路径规则取 sink，见 §0.4），未读 `codeFlows`；[semgrep_to_findings.py](file:///f:/Coding/audit-driven-development/scripts/semgrep_to_findings.py#L79) 的 `convert_semgrep_result` 产出的 `evidence` 仅有 `file/line_start/cwe/owasp/rule_id/source` | **精确 source 不可得** → MVP 必须有"无 source 时的语义" |
| **GAP-2** | 现有 claim 分类对 SAST 转换后的 finding **不触发 taint** | 转换器生成的 claim 形如 `{rule_id}: {message} ({cwe}) — affects {path}:{line}`（[CLAIM_TEMPLATE](file:///f:/Coding/audit-driven-development/scripts/semgrep_to_findings.py#L45)），如 `...Dangerous subprocess use (CWE-78)...` **不含 taint 关键词** | 纯文本 `TAINT_PATTERNS` 命中率低 → 必须引入**结构化信号**（CWE / 分析模式标记） |
| **GAP-3** | `ast_cfg.py` 只有控制流（CFG），无数据流（DFG） | `CFGBuilder`（[L33](file:///f:/Coding/audit-driven-development/scripts/ast_cfg.py#L33)）追踪语句可达性；`is_reachable`（[L202](file:///f:/Coding/audit-driven-development/scripts/ast_cfg.py#L202)）为 BFS 可达 | Tier 2 兜底需**新建** def-use 链追踪，工作量不可低估 |

### 0.4 外部事实核验（本步新增，已追溯）

| 事实 | 结论 | 来源 |
|------|------|------|
| CodeQL SARIF 携带 taint 路径 | ✅ `codeFlows[].threadFlows[].locations[]`；一手文档原文："This array **may** be populated with one or more `codeFlow` objects **if the query that defines the rule for this result is of `@kind path-problem`**"（即条件性生成，非必然） | [GitHub Docs · CodeQL CLI SARIF output](https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli/sarif-output)（Step 4 逐字复核） |

| Semgrep 携带 taint 路径 | ✅ 存在 `dataflow_trace`（含 `taint_source` / `intermediate_vars` / `taint_sink`）字段，但为 **Pro Engine** 能力；Semgrep CE 仅单函数 taint。**Step 4 复核证据**: 官方对比页原文 "Semgrep CE provides … **Single function taint analysis**"；术语表 "Semgrep CE is limited to per-file analysis"；taint 文档 "Using the CLI option `--pro`, Semgrep will perform interprocedural (across functions) as well as inter-file (across files) analysis" | [semgrep_output_v1.jsonschema](https://raw.githubusercontent.com/semgrep/semgrep-interfaces/main/semgrep_output_v1.jsonschema) · [Semgrep CE vs Platform](https://semgrep.dev/docs/semgrep-pro-vs-oss) · [Taint analysis 文档](https://semgrep.dev/docs/writing-rules/data-flow/taint-mode/overview) |
| Joern 数据流 API | ✅ `reachableBy` / `reachableByFlows` / `source` / `sink` 均为官方 Complex Steps | [Joern CPGQL Reference Card](https://docs.joern.io/cpgql/reference-card/) |

**核验结论**: 上述外部事实支持"**精确 source 常常不可得**"这一判断 —— 路径信息依赖上游工具的分析模式（CodeQL 需 path-problem 规则、Semgrep 需 Pro），且 ADD 当前转换器并未保留原始 payload。故 MVP 必须设计**不依赖 source 的退化语义**（见 §2.3）。

## 1. 设计决策

> 每条决策含：决策 / 理由 / 后果 / 追溯。标注 ⚠️ 的为**需用户确认**项。

### D-T9'-1: 新增结构化 + 文本双通道的 taint claim 识别

- **决策**: `classify_claim(claim, evidence=None)` 新增可选参数 `evidence`。命中以下**任一**通道即标记 `"taint"`：
  - **通道 A（结构化，优先）**: `evidence["analysis_kind"] == "taint"`，或 `evidence["cwe"]` ∈ `TAINT_CWE_SET`
    > **MVP 可达性（v1.3 补充）**: 子条件 `analysis_kind` 在 `scripts/**` **零生产者**，且 D-T9'-6 明确"MVP 不修改任何 SAST 转换器" ⇒ **该子条件在 MVP 不可达**，标注为 **Phase 2 预留接入点**（不删）。MVP 阶段通道 A 实际仅由 `evidence.cwe` 承载，且仅在生产链路（转换器输出的 finding）上可达 —— 见下条"可用性限定"。AC-4b 以合成 evidence 覆盖该子条件。
  - **通道 B（文本，兜底）**: `TAINT_PATTERNS` 命中 claim 文本
- **`TAINT_CWE_SET`（可配置集合）**: `CWE-78`（OS 命令注入）、`CWE-79`（XSS）、`CWE-89`（SQL 注入）、`CWE-94`（代码注入）、`CWE-22`（路径穿越）、`CWE-502`（不安全反序列化）、`CWE-918`（SSRF）、`CWE-611`（XXE）
  > **取证状态（v1.2 标"启发式初值"；v1.3 已逐项取证完成）**: 8 项**全部**获得上游 `@kind path-problem` 一手证据（CodeQL Python query help 逐页核验，见 [C1–C4 裁决分析 E-1](file:///f:/Coding/audit-driven-development/docs/research/2026-10-20-T9prime-C1-C4-decision-analysis.md)）：
  > `078→py/command-line-injection`、`079→py/reflective-xss`(high)、`089→py/sql-injection`(high)、`094→py/code-injection`(high)、`022→py/path-injection`(high)、`502→py/unsafe-deserialization`、`611→py/xxe`、`918→py/partial-ssrf`(**medium**)。
  > **两条必读限定**:
  > ① **CWE-918 上游 precision 为 `medium`**（其余为 high），须差异化对待；
  > ② "CWE ∈ 集合 ⇒ taint 断言"**仅在该 CWE 由 taint-mode / `path-problem` 规则报出时成立**；对**数据集标签 CWE**（bigvul / cvefixes 语料）**不成立** —— 详见 §7 R9。
- **理由**: 缺口 GAP-2 —— 转换器产出的 claim 不含 taint 关键词，纯文本通道命中率低；而 `evidence.cwe` 由 T5（`cwe_rules.enrich_finding_with_cwe`）已经填充、两个转换器也会产出（[semgrep L110](file:///f:/Coding/audit-driven-development/scripts/semgrep_to_findings.py#L110)、[codeql L139](file:///f:/Coding/audit-driven-development/scripts/codeql_to_findings.py#L139)），**实现成本为零**。
  > **可用性限定（v1.3 补充，纠正 v1.2 的过度乐观）**: 该信号在**生产链路上可用**，但在**现存 benchmark 语料上不可用** —— `docs/benchmark/**` 中 `"cwe"` / `"rule_id"` / `"owasp"` 三键**零命中**，882 条语料无一来自 SAST 转换器（[裁决分析 E-2](file:///f:/Coding/audit-driven-development/docs/research/2026-10-20-T9prime-C1-C4-decision-analysis.md)）。故通道 A 的收益**在当前基准上为 0**，其验证须待 Phase 2（T12）引入 SAST 转换器语料；MVP 阶段仅由单元测试（AC-2 / AC-4b）覆盖。
- **后果**: claim 类型集合可能出现 `["taint", ...]` 叠加；因 `classify_claim` 原为"多类型叠加"语义，叠加本身不破坏既有类型。
- **不变式（v1.2 修正）**: `evidence=None`（默认）时**仅结构化通道（A）不激活**；**文本通道（B）是本步有意新增的能力**，因此 `classify_claim` 的**输出不再是 v2.8 的逐位超集相等**。v2.8 的**逐位一致性由 kill switch 保证**：`ADD_TAINT_DISABLE=1` 时 taint 识别与分派全部关闭 ⇒ 全量裁决与 v2.8 逐位相同（见 AC-9）。
  > 原 v1.0 曾写"`evidence=None` 时行为与 v2.8 逐位一致"，与通道 B 的实现逻辑冲突（通道 B 不依赖 `evidence`），属**自相矛盾**，由 Step 4 审计发现并修正。
- **追溯**: 调研 §5.2；代码 [classify_claim L103](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L103)、[IMPORT_PATTERNS L61](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L61)、[semgrep_to_findings.py](file:///f:/Coding/audit-driven-development/scripts/semgrep_to_findings.py)（T5 CWE 填充）

### D-T9'-2: 以 L4 内新增 `taint` 分支承载 L5 语义（⚠️ ADR-005 调和）

- **冲突**: ADR-005 规定"T9' 采用 **L5 层架构（独立层级）**"；调研 §7.2 建议"在 `verify_l4_structural` 内新增 `taint` 分支（最小侵入）"。二者字面冲突。
- **决策（调和）**:
  1. **语义层独立**：新增 `_verify_l5_taint(...)` 独立函数（L5 调度层），并对外暴露独立三态字段 `taint_verified`（满足 ADR-005 的"独立层级"与 ADR-012 的三态）。
  2. **机制层复用**：该函数由 `verify_l4_structural` 调用，结果写入现有 `checks["taint"]`，复用既有聚合器（[L444-L472](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L444-L472)），**不新建并行管线**。
  3. **编号层不变**：`verification_level` 数值域保持 `1..4`（**不引入 5**）。L5 是"层"的架构标签，通过 `taint_verified` 字段体现，而非数值等级。
- **理由**: 新建独立管线会复制聚合/降级/接线逻辑（成本 × 风险 ×2），且无收益；而数值域引入 5 会破坏下游消费方对 `verification_level ∈ {1,2,3,4}` 的既有假设。
- **后果**: 需在 Step 7 checklist 中确认无消费方依赖 `level==5`；`taint_verified` 为**新增字段**（只增不删）。
- **追溯**: [ADR-005 L143-166](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L143-L166)、[ADR-012 L316-331](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L316-L331)、调研 §7.2

### D-T9'-3: 无 source 时采用 broad-source 语义（MVP 主通道）

- **决策**: `source` 不可得时，以**宽来源集**执行 `sink.reachableBy(sources)`，其中
  ```
  sources = cpg.call.name(INPUT_API_REGEX)  ∪  cpg.method.parameter
  ```
  `INPUT_API_REGEX` 为可配置集合，**仅允许 call 形状的名字**（v1.4 修正，E-2）：**`input|raw_input|getenv|getpass|get|getlist`**。
  > **T0 实测定稿（M-1，2026-10-20）**: 实测证实 pysrc2cpg 把**点分调用渲染为末段名**（`os.getenv` → call name `getenv`；`os.system` → `system`）⇒ `request.args.get` / `os.environ.get` 渲染为 **`get`**，故 `get|getlist` 有依据；`input` / `getenv` 已实测命中；**`loads|load` 已删除**（无实测依据，且 `pickle.loads` / `yaml.load` 属 **sink 侧**语义，列入来源集是错的）。实测记录见 [api-validation](file:///f:/Coding/audit-driven-development/docs/audit-log/2026-10-20-T9prime-joern-api-validation.md) §2⑥。
  > 另: 原始 E-2 修正说明记 v1.3 曾写 `input|raw_input|sys.argv|os.environ|getenv|getpass|request.(args|form|…)` —— 其中属性访问不是 `cpg.call` 节点，写进 `cpg.call.name(regex)` **永远匹配不到**；属性型输入由 **`cpg.method.parameter`** 覆盖。
- **语义**:
  - `verified=True`  —— 存在从宽来源集到 sink 的数据流 ⇒ 该 finding 的 taint 断言与 CPG 一致
  - `verified=False` —— sink 节点已定位 且 宽来源集**无任何路径**到达 ⇒ 结构性证伪
  - `verified=None`  —— sink 未定位 / Joern 不可用 / CPG 生成失败 / 查询失败 / 宽来源集为空
- **理由**: 缺口 GAP-1 —— 精确 source 在 MVP 阶段不可得（转换器不保留 payload）。宽来源集是 0 上游改动即可执行的真实污点检查；且 `False` 的方向是**安全**的：只有当 sink 的入参连"任何可能污点来源"都触达不到时才证伪。
- **关键保护**: `sink_nodes == 0`（未定位 sink）必须返回 `None` 而非 `False`，否则会把"找不到节点"误判为"污点不可达"。
- **后果**: 精度低于精确 source→sink（过近似来源会多判 True）；但**假阴性风险主要来自跨过程与自定义语义缺失**（见 §7 风险 R2/R3）。
- **追溯**: 调研 §2.1/§2.3；[Joern dataflow-semantics 的 sound-but-imprecise 说明](https://docs.joern.io/dataflow-semantics/)

### D-T9'-4: MVP 阶段 taint 证伪默认只降级、不移除（⚠️ 与 ADR-018 局部偏离）

- **决策**: 新增 check 字段 `disproof_action`，取值 `"remove" | "downgrade"`。
  - **既有类型（dead_code / import_related）不设该字段 ⇒ 默认 `"remove"`，行为与 v2.8 逐位一致**（满足 ADR-018）。
  - **taint 类型 MVP 默认 `"downgrade"`**：`taint_verified=false` → `action="partial"`（P0→P1 降级），**不进 hallucination_log 删除路径**。
  - 提供显式开关 `--taint-disproof=<downgrade|remove>` 与 env `ADD_TAINT_DISPROOF`（默认 `downgrade`）以便在 benchmark 证据充分后切换。
- **必要实现要件（v1.2 补充，否则本决策不成立）**: [structural_false 判定 L746-L749](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L746-L749) 当前为
  ```python
  any(isinstance(c, dict) and c.get("tier", 3) <= 2 and c.get("verified") is False
      for c in checks.values())
  ```
  该判定**只看 tier 与 verified**，与 `disproof_action` 无关。若不扩展为"同时要求 `c.get("disproof_action", "remove") != "downgrade"`"，则 taint 的 tier≤2 `verified=False` **仍会命中 `unverified`（移除）路径**，与"默认只降级"直接冲突。
  > v1.0 仅描述了字段与后果、**未声明该判定式必须修改**，属设计要件缺失，由 Step 4 审计发现并补齐（这正是 v2.7.3 已记录的"dead parameter"反模式：新增字段若不改变判定逻辑，则字段是死的）。
- **理由**:
  1. GAP-3 + 跨过程缺失 ⇒ Tier 2 AST 的 `False` 存在**系统性假阴性**（若 sink 由另一函数写入，AST 会误判不可达）；
  2. ADR-012 明确写的是"降级**或**移除"，本决策落在其允许范围内，非违背；
  3. 对一个"不信任系统"而言，**误删真阳性**的代价高于漏删假阳性。
- **后果**: G2 在 MVP 阶段为"部分修复"（可降级、可标记，不可过滤删除）；切换默认值需 benchmark + 标注样本证据（见 §9 AC-9/AC-10）。
- **追溯**: [ADR-012 L316](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L316)、[ADR-018 L426](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L426)、[structural_false 判定 L746](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L746)

### D-T9'-5: "无裁决不落 check" 的加法式聚合不变式

- **决策**: taint 分支遵循严格不变式 —— **只有当某一层能产出真实裁决（`verified` ∈ {True, False}）时才向 `checks` 写入 `checks["taint"]`；否则完全不写入**。
- **理由**:
  1. 聚合器对 `checks` 内容敏感（[L444-L472](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L444-L472)）：写入 `verified=None` 的 check 会让 `any_structural_none` 分支被激活，在"其余结构化检查全为 False/None 且存在 Tier 3 检查"等条件下**可能改变既有 finding 的裁决**（注意：是"可能"，非必然；v1.0 原文写作"改变"，属过强断言，已由 Step 4 审计修正）；

## 2. 语义定义

### 2.1 裁决方向约定（与既有类型对齐）

ADD 的 `verified` 语义是"**该 finding 的断言是否被源码证实**"：

| 类型 | `verified=True` 含义 | `verified=False` 含义 |
|------|---------------------|----------------------|
| dead_code | 确认是死代码 | 确认不是死代码 |
| import_related | 确认存在导入环 | 确认无环 |
| **taint（本步）** | **确认 source/宽来源集可达 sink**（断言成立） | **确认污点触达不到 sink**（断言被证伪） |

→ 与既有约定一致，不引入反向语义。

### 2.2 三态输出（ADR-012 落地）

| 状态 | 触发条件 | 对 finding 的动作 |
|------|---------|------------------|
| `taint_verified=true` | 路径存在 | 保留（`action="verified"`，与既有聚合一致） |
| `taint_verified=false` | sink 已定位 且 无路径 | **降级**（`action="partial"`，MVP 默认，见 D-T9'-4） |
| `taint_verified=null` | 不可判定（任一降级触发条件） | 保留（**不写 check**，行为同 v2.8） |

### 2.3 来源解析策略（分层，先精确后宽泛）

```
S1 精确模式 (taint_mode="exact")
   条件: source_file/source_line 可得（finding.evidence.source_line，或调用方显式传入）
   语义: sink.reachableBy(sourceNode)

S2 宽泛模式 (taint_mode="broad")   ← MVP 默认
   条件: source 不可得，但 repo_root + sink_file + sink_line 可用
   语义: sink.reachableBy(INPUT_API_REGEX 调用 ∪ 全部 method.parameter)

S3 不可判定 (taint_mode=null)
   条件: 缺少 repo_root / sink_loc / Joern 不可用 / CPG 失败 / 查询失败 / 宽来源集为空 / sink_nodes==0
   语义: verified=None（不写 check）
```

**S2 的合理性论证（为什么"宽来源"仍可证伪）**: `verified=False` 要求把**全体函数参数**与**输入 API 调用**都当作污点源后，仍不存在任何到达 sink 的路径。此时该 sink 在 CPG 层面与任何外部输入均无数据流关联 —— 这是对"外部输入驱动的注入类漏洞"断言的实质性证伪。至于**跨过程**传播导致的漏判，由 D-T9'-4（只降级）吸收风险。

### 2.4 claim 类型与既有类型的优先级

`classify_claim` 保持"多标签叠加"语义，`taint` 追加在 `import_related` 之后：

```
["missing"] ["wrong"] ["violates"] ["dead_code"] ["import_related"] ["taint"] ["hallucination_pattern"]
```

**已知既有缺陷（记录，不在本步范围内修复）**: `VIOLATES_PATTERNS`（[L44](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L44)）与 `IMPORT_PATTERNS`（[L61](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L61)）都包含 `circular (dep|dependency|import)`，导致同一 claim 同时被标 `violates` 与 `import_related`。此为 v2.7 遗留，修复会改变既有裁决 ⇒ **另立任务**，本步不动。

## 4. 分级降级策略（完整决策表）

| 层 | 条件 | 产出 | 落 check | 后续 |
|----|------|------|---------|------|
| T1 Joern | 可用 + CPG 成功 + sink 定位 + 有源 | `verified=True/False` | ✅ tier=1 | 结束 |
| T1 Joern | 上述任一不满足 | `verified=None` | ❌ | → T2 |
| T2 AST | `language=="python"` 且 T1 非 True | `verified=True/False` | ✅ tier=2 | 结束 |
| T2 AST | 解析失败/无外层函数/无污点集 | `verified=None` | ❌ | → T3 |
| T3 regex | 能提取 sink API 名 | `verified=True/False` | ✅ tier=3 | 结束 |
| T3 regex | 提取失败 | `None` | ❌ | **不写 check**（行为同 v2.8） |

**降级一致性约定（对齐既有实现）**: T1 `verified=True` 时**不**降级（沿用 import 分支的"仅 True 阻止降级"约定，[L403](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L403)）；T1 `verified=False` 时**仍**执行 T2 做双重校验（沿用 dead_code 分支的双检约定，[L358-L359](file:///f:/Coding/audit-driven-development/scripts/verify_findings.py#L358-L359)）。

> **聚合取向已由 Step 5 定稿（v1.4 修订，G-6）**: `T1 False + T2 True` ⇒ **取 T2（True）**，即**保守向**（不产生证伪、不触发移除）；`T1 False + T2 False` ⇒ 取 T1；`T1 None + T2 any` ⇒ 取 T2。
> **原 v1.x 措辞"聚合取更强证伪者"与本定稿矛盾** —— 强证伪（T1 `False`）在跨过程假阴性风险下**不被优先采纳**：T2 的 True 表示"sink 所在函数内确有参数/输入流"，而 T1 的 False 可能源于前端（pysrc2cpg）能力缺口。误删真阳性的代价高于漏删假阳性（D-T9'-4 / [ADR-027](file:///f:/Coding/audit-driven-development/docs/DECISIONS.md#L615)）。

### 13.6 Step 10 回写记录（T0.7 codeFlows 次序闭合，2026-10-20）

**背景**: §13.3 曾将"CodeQL `codeFlows` 的 source/sink 次序"保留为 ⚠️ 未证实（§13.1 H5 的降级项）。Step 10 验收时该项在 checklist 中为 **T0.7（唯一 P2「未执行」项）**，本步予以闭合。

**方法与结论**（本机**无 CodeQL CLI**，T0 探针亦非 SARIF 路径 ⇒ 采用"权威样例 artifact 观测 + 一手查询语义交叉"）:

| 证据 | 结论 |
|---|---|
| **A. 样例 SARIF 观测（次序）** | `codeFlows[0].threadFlows[0].locations[]` 的**首项 = source**（`:38  command = request.json['command']`，message "User input received…"）、**末项 = sink**（`:42  subprocess.run(command, shell=True, …)`，message "Unsanitized value passed to…"）⇒ **次序 = source → sink** |
| **B. 同一 artifact 的主位置** | `result.locations[0].physicalLocation.region.startLine = 42` = **sink 行** ⇒ 主位置 = sink |
| **C. 一手查询语义（端点角色）** | CodeQL 路径查询 `select` 为**四列** `select element, source, sink, string`；官方模板与内置 [`py/command-line-injection`](https://codeql.github.com/codeql-query-help/python/py-command-line-injection/)（`@kind path-problem` / `precision: high`）**均取 `sink.getNode()` 作首列**，且官方明确"告警可显示在 source 或 sink，取决于判断" ⇒ **主位置由查询作者选择；CodeQL 路径规则惯例取 sink，非规范强制** |
| **D. 生成条件（复核）** | `codeFlows` 仅当规则为 `@kind path-problem` 时**可能**生成（GitHub 一手文档，Step 4 已逐字复核） |

**连带修正**: §0.4 事实表该行 ⚠️ → ✅；GAP-1 括号内"主位置=**通常**是 sink"精确化为"**主位置 = `select` 首列（CodeQL 路径规则取 sink）**"；§8 实测摘要 ⑦ ⚪ → ✅。

**证据强度声明（诚实披露）**: A/B 取自 **SARIF SDK 维护方（Microsoft，SARIF TC 编辑方）随文档发布的样例 artifact**（[`sarif-sdk/docs/ai/example.sarif`](https://raw.githubusercontent.com/microsoft/sarif-sdk/HEAD/docs/ai/example.sarif)），**非 CodeQL 产出物**；本机无 CodeQL CLI 无法端到端复现；SARIF 规范 `codeFlows` 正文（§3.27.18）因页面体积**未能完整取回** ⇒ 本条为**"样例观测 + 规范语义交叉"级证据，不等于实机实测**。详细证据表见 [T0 实测记录 §2⑦](file:///f:/Coding/audit-driven-development/docs/audit-log/2026-10-20-T9prime-joern-api-validation.md#L139)。

**风险判定**: MVP **不消费** `codeFlows` / `dataflow_trace`（D-T9'-6）⇒ 本项闭合**不改变任何设计决策**、**不触发**任何 Tier 降级分支。Phase 2（T12）若消费，须以 A/B 观测 + 上游实现为准，并在转换器内**显式校验**端点，**不得静默假定**次序。
